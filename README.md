# MURVC Club Manager

MURVC's club management system for WordPress, integrating Ultimate Member (accounts/profiles) and WooCommerce (payments via Square). The admin splits into three areas:

- **Club Membership** — club-wide member list, time-bound membership tiers, membership history reporting, stats and logs
- **VVL Oversight** — competition machinery: teams, trials, coach selections, team assignments, fees and payments, player readiness
- **Club Programs** — attendance for casual programs (Mixed Development and anything else sold as a product with date variations)

> The plugin folder is still `team-oversight-migration` and the constant is `TEAM_OVERSIGHT_VERSION`; the display name changed in 1.33.0. Renaming the folder/slug is a deliberate cutover-day job (it deactivates the plugin and changes the deploy path).

## Requirements

- WordPress 5.0+, PHP 7.4+
- Ultimate Member (profiles, registration, login)
- WooCommerce with legacy (CPT) order storage — HPOS is not currently supported by the kit-purchase detection

---

## Club Membership

### Membership tiers

Memberships are **time-bound grants** stored in `team_memberships`: tier + start/end date + source (`purchase` / `manual` / `import`). A member's current status is their highest unexpired grant. Three tiers:

| Tier | WP role | How granted | Expiry |
|------|---------|-------------|--------|
| Life Member | `life-member` | Manual only | Never (2099 sentinel, shown as "no expiry") |
| Full Member | `full-member` | Purchase, manual, or automatic on team assignment | Term from purchase date; assignment grants run to 1 April of the year after the season |
| Associate Member | `associate-member` | Purchase or manual | Term from purchase date |

- **From purchases**: set "Membership tier granted" + "Membership term (months)" on a WooCommerce product (Product → Edit → General), or configure product-category rules on the Members page. Only explicitly configured products grant anything. Terms run from the purchase date; overlapping grants simply overlap (highest active tier wins).
- **From team assignments**: anyone with an active team assignment (any role — player, training only, coach, assistant coach, team manager) for the current season or later is automatically granted Full Membership running to **1 April of the following year** (`source = assignment`) — so a 2027 VVL player stays a member until the 2028 teams are finalised just before April 2028. (Before 1.67.0 these ran to 31 Dec; a one-off update moved every still-running team grant to the new date, logged per person.) Synced immediately after plugin admin changes and by the daily cron; deduped per person per season, and removing someone from a team never revokes the grant.
- **Role sync**: the `full-member`/`associate-member`/`life-member` WP roles are kept in sync on every grant and by a daily cron (`team_oversight_membership_sync`), including automatic demotion when the last grant expires. Users with roles but **no** ledger rows are never touched (protects pre-ledger role assignments until seeding runs).
- **Seeding**: Members page → "Seed memberships from this year's purchases" converts the year's qualifying paid purchases into dated grants. Only Processing/Completed orders count, never failed, cancelled or refunded orders or refund records. A dry run is available and it is idempotent. Grants an earlier run made from such orders are not removed: they are listed under **Grants to review**.
- **Order re-scan**: Members page → "Re-scan this year's paid orders" replays every paid order through the grant logic with the *current* product/category configuration — run it after adding membership attributes to a product, since orders paid before the attributes were set granted nothing. Idempotent; backfilled grants are dated from the order's paid date. (Grants require the order to reach Processing/Completed *and* be linked to a WP account — guest orders never grant.) It works through the orders in pages of 200, clearing WordPress's in-request cache between pages so memory stays flat. After about 20 seconds it stops and shows a **Continue re-scan** button, which carries on from the last order checked.
- **Refunds and cancellations**: a refunded or cancelled order never ends a membership by itself. Each grant the order gave is logged once as **Order refunded or cancelled** on Club Membership → Logs, with the order number, refund amount, tier and grant number. A partial refund flags only the grant whose line it refunds, or every grant on the order when the refund has no lines. The Members page lists these under **Grants to review**: grants whose order is refunded, cancelled, failed or otherwise unpaid, grants on refund records, and grants whose line was later refunded. A grant on a refund record (made by the early purchase-history seeding) is a second grant on top of the original order's, dated from the refund, so it usually runs past the original. Grants not yet expired are listed first; expired ones are folded behind a count. The list is read-only and never clears itself; the club decides whether each grant stands.
- The `[murvc_member_role]` shortcode (registered by the plugin) shows the profile owner's tier badge on Ultimate Member profiles.

### Admin dashboard

The WP dashboard is replaced (for admins) with a fast **MURVC Club Overview** widget: current members, fees outstanding, overdue people/amount (each fee on its own season's schedule; from 2027 the player's own), trial applications awaiting action, people on teams — each tile linking to its admin page — plus the latest activity-log entries and quick links. The slow stock widgets (WordPress news, WooCommerce status/report queries, quick draft, activity, Solid Security panel) are removed; the widget itself renders from the plugin's indexed tables in a few milliseconds.

### Members page (Club Membership menu)

One row per person: membership status + expiry, age, gender, MUS category, VVL teams for the season, fees owing, VA accreditation, profile-confirmation status. Filter/search/sort, CSV export, manual grant (with email autocomplete) and revoke. Revoke is refused, with the reason, for anyone on an active team for the current season or later: team members are Full Members until 1 April after their season, and the sync would re-grant straight away. Take them off the team first. Active status is judged on the site's date, not the database clock.

### Member Lookup

Club Membership → Member Lookup: search **any account on the site** — not just people on the membership ledger — and get everything the club holds about that one person on a single screen. Emergency contacts sit at the top (both of them, phone numbers repaired and tap-to-call), followed by profile details, membership grant history, every team assignment across all seasons, fees with the payment ledger, credit, what's due by today and the overdue amount (each season on its own schedule: the season-long one for 2026 and earlier, the player's own from 2027), trial applications, recent WooCommerce orders and recent activity-log entries.

Search matches display name, email, username, first/last name, mobile, student ID **and emergency contacts** — so an unknown number that rings the club can be traced back to whose contact it is. When a result matched on someone else's details the row says so ("emergency contact: Jane Smith — 0411 222 333") rather than looking unexplained.

Phone matching compares digits to digits, so formatting never gets in the way: `0411 222 333`, `0411222333`, `411222333` and `+61 411 222 333` all find each other. That covers both the imports that dropped the leading zero and the profiles saved with spaces or a country code.

Deliberately search-first: with thousands of accounts the page never lists them all. Nothing is queried until you type at least two characters, results are capped at 25, and the detail view costs one person's worth of queries (a search runs in ~20ms against ~3,800 accounts). The **Profile** button on the Members page opens this view.

**Fee timeline card** (1.70.1, admins only): for a 2027-or-later season, a card-wide *Fee timeline* card after Fees shows and edits the person's team places for that season. It opens on their latest 2027+ season with a place or an invoice (links switch between seasons); a link with `&season=YYYY#fee-timeline` jumps straight to it, which is how Payment Management's names and Team Assignments' *Fee timeline* buttons open it. For an earlier season it only says that fee timelines start with the 2027 season. The card shows:

- **Header**: the season dates and how many days fees cover, the payment window (*season dates* when blank; it sets each player's due dates and the late-join cutoff), the late-join cutoff, and whether fees are released.
- **Warnings**: a place with no start recorded (charged from the day it was added until one is saved), a start after the late-join cutoff, and a place *recorded outside the timeline* (no *added* entry in its history, so something other than these screens inserted it, or changed the team or role of a place made before 1.70.1; a direct change to a place's dates leaves no trace on the card). Places from before 1.70.1 get a quieter *placed before the fee timeline* note asking for their dates to be checked once.
- **Bars**: one lane per team and role across the season, with the payment window shaded, a line for today, a marker at each stop, the part still to come hatched, and a *start not recorded* badge. The bars wrap on a narrow screen.
- **For each place**: start and stop dates with Save; **Stopped playing on** (*Stopped on* for staff; defaults to today, may be past or future; keeps the place and charges up to the day before) or **Clear the stop**; **Change role or team from [date]** (stops the old place and starts the new one that day; a date on or before the place's start corrects it instead); and **Remove (added by mistake)**, which needs a tick box and treats them as never on that team, so it charges nothing. Each has a **Preview** button that shows the fee change, and what falls due by today, without saving (*If saved: Fee $X → $Y · due now $A → $B*; the due part once they have an invoice). A save that loses to someone else's change, or a page left open, changes nothing and says to reload.
- **How the fee is worked out**: each stretch from its first to its last day charged, with its days, the places held, the rate and the amount, and the total.
- **Money**: the fee (marked when set with Edit Fee, with the calculated amount), paid from the ledger, credit, outstanding, due by today on the player's own schedule (with their window explained), overdue, the next payment date or how long they've been behind (saying so when the behind clock was held back to when the fee or a change was recorded), status, and the same fee pill coaches see.
- **Change history**: every change to the person's places that season, with when, who (or the daily job), the old and new dates, and the fee before and after.

Every save is re-priced straight away (once fees are released), logged as *Team dates changed* on VVL Oversight → Logs, and leaves a notice at the top of the card. Saving works without JavaScript; only Preview uses it.

### Stats

Club Membership → Stats — statistics about **current members** (unexpired ledger grants), in tabs designed to grow over time:

- **Data Quality**: profile completeness — gender, DOB, mobile, MUS category, this-year confirmation — as percentages with colour bars and 30-day deltas. A snapshot is recorded once a day (membership cron, page-view fallback, manual button) into a non-autoloaded option capped at ~3 years, so sparkline trends accrue from first deploy.
- **Locations**: postcode distribution (UM `postal_code`, falling back to the WooCommerce billing postcode; messy values like "VIC 3000" are normalised), plus a saved **postcode watchlist** — enter any list of postcodes and see how many members live in them. Defaults to current members; a date-range picker widens the population to anyone who held a membership during the period.

### Membership History

Club Membership → Membership History: pick a date range and see everyone whose membership overlapped it — highest tier held, every membership period with dates and source, age/gender/MUS, current status. CSV export. History exists from the moment grants exist (run seeding to backfill).

The **MUS Matrix** tab on the same page produces the periodic MUS return: active members (anyone holding a membership grant in the date range) as a matrix of MUS eligibility category × gender (Male / Female / Non-Binary / Unknown) with totals, CSV export. Profile category variants fold into the MUS row labels (other-university student/alumni variants merge; junior/high-school count as Other; missing data counts as Unknown; unrecognised categories keep their own row rather than being lumped).

The **VV Report** tab produces the VV return: age band (10-year bands, age at the end of the period; missing DOB → "Unknown DOB") × gender (Male / Female / Other / Unknown gender) with totals, CSV export. Defaults to Associate members only, with tier checkboxes to change what's included; each person counts once under the *highest* tier they held in the period, so tier selections never double-count.

### Duplicate accounts (1.71.0)

Club Membership → Duplicate accounts finds people who have more than one account and merges them into one, with a preview first and an undo afterwards. Nothing is asked of members: duplicates are flagged to admins here rather than at registration (a member rarely knows which old email an account is under).

- **Suggestions**, in three tabs. **Strong**: same name and date of birth; the same name, no birth date to compare, and a shared phone, email (gmail dots and +tags ignored) or student number; or a near name (a surname typo, first and last swapped) with the same birth date and a shared contact. **Likely**: a near name with the same birth date (a near *first* name with the same surname and birth date, like Sam and Samuel, is never Strong and is flagged *could be twins or siblings*, because Ella and Bella look the same), or the same name with a birth date one digit apart and something shared. **Possible**: little more than the name matches. Accounts are never put together, in any tab, when their birth dates differ (a parent and child with one name), when they share a surname and birth date but not a first name (twins), when only one says Jr or Sr, when the same surname and birth date are recorded as female and male, or when an admin marked them as different people; a group that might be a parent and child with one name, or records different genders, says so. The list is worked out from every account at once and kept for 15 minutes (*Look again now* refreshes it); groups first seen in the last 14 days are marked **New**, and their count shows on the menu (refreshed a few minutes after accounts change, and daily). Each group shows, per account: the email and login, birth date and mobile, when it joined and was last seen, its orders, club records (team, fees, trials by season) and membership, with any account that never confirmed its email, is awaiting review or belongs to staff marked. The most recently used account is suggested as the one to keep.
- **Search** (name, email, login, mobile or account number) narrows every tab to groups with a matching account; the tab counts show how many matches each tier has. Words can be in any order, case and accents don't matter, a mobile matches in any format or by its last six or more digits, and `449` or `#449` is an account number. Merge history searches the accounts as they were when merged, so a deleted account is still found by its old name or email.
- **Preview merge**: pick the account that lives on (*Keep*) and untick any account to leave out. The preview lists what moves (orders, club records, membership grants, payments), which profile fields are copied (only into empty fields on the kept account; an address, billing or shipping block is copied whole or not at all, never mixed), the conflicts where the kept account wins, both emergency contacts kept, the membership roles before and after, and which logins stop working. It is **blocked** when the kept account is deactivated or rejected in Ultimate Member, an account being merged away has a staff role or is the one you're logged in with, two of the accounts hold club records for the same season (fix those first), an account has more than 400 orders (use WP-CLI) or has WooCommerce API keys or a pending privacy request. When both accounts have fee history for the same season (from team places, now or in the past), the preview says they can't be merged here: fee history is never deleted, so nothing in the admin pages can clear that clash, and those accounts are left for the website maintainer. Up to six accounts merge into one at a time. Different birth dates (between any two of the accounts), different first names, or an account an admin deactivated or rejected, need a tick to confirm. Nothing changes until **Merge**, and the merge refuses if anything changed since the preview.
- **Merge** runs in one database transaction: the other accounts' orders (through WooCommerce, with an order note, and in Analytics), club records, payments, grants, attendance, coupon uses, saved Square cards (moved only when they belong to the same Square customer), comments and profile photo move to the kept account, which takes the earliest join date; then the other accounts are deleted quietly (no emails). Money is never re-priced or re-calculated: rows change owner, not amount. The kept account records which accounts were merged into it. During a merge the other accounts are signed out and can't sign in.
- **Merge history** keeps a full backup of each merge. **Undo this merge** brings the deleted accounts back with their own numbers, logins and passwords, and moves back everything that still points where the merge put it. On the kept account it puts back only what the merge changed (the details it filled in, its join date and name, the roles it added or removed, committee access and Club Program supervisor places, "not the same person" decisions), and only where those still hold what the merge wrote: anything changed since is left and listed. It never puts back sign-in or security settings. Undo the newest merge first: a merge can't be undone while a later merge involves the kept account, or once the kept account itself has been merged away, or when the kept account has new records since (team places, fees, payments, trial applications) in a season the merge moved, which would split that season across two accounts.
- **Not the same person** on a group marks those accounts as different people so they are never suggested together again (reason: same name, twins or siblings, parent and child, other); **Not duplicates** lists them with *Suggest again*. **Merge by ID** merges accounts the list never suggested.
- WP-CLI: `wp club-manager accounts duplicates|preview|merge|undo|history` (run with `--user=<admin>`), for the same checks, backup and undo.

Each merge, undo and *Not the same person* is logged on Club Membership → Logs (*Accounts merged*, *Account merge undone*, *Marked not duplicates*).

## VVL Oversight

### Teams (Configuration page)

Teams are configured **per season** (1.48.0+) with a **code** (stable internal ID — never shown to players), **name** (what players see), **gender** (men's/women's/mixed), **age eligibility rule** and **playing-shirt count**:

- **Per season**: the Configuration page's season selector decides which season's list you are editing. Adding, renaming, re-ruling or deleting a team changes that season only — 2027's SL3M-R and 2026's SL3M-R are separate entries. Internally the registry is keyed `CODE-YYYY`; assignments, applications and selections keep the bare code plus their own season, so nothing historical is rewritten and a code still identifies "the same team" across years.
- **Deleting** is blocked only by active assignments *in that season*. Removing a team from 2027 while people are still assigned to it in 2026 is fine — that was the bug this replaced.
- Age rules follow the VVL By-Laws and compute their DOB cutoff from the season year automatically (nothing to update each season): **U19** = no 19th birthday during the season year; **U17**/**U15** (YSL) = 16/14 or younger as of 31 August.
- Shirts: how many playing shirts a player must pay for on this team (Premier 2, YSL 0 — supplied, default 1).
- **Division level** (1.76.0): a number per team saying which division it is (lower = higher), used to suggest lower divisions to players who were not selected. Defaults by team code: Premier League 1 = 1, Premier League 2 = 2, JPL = 3, State League 1 = 4, 2 = 5, 3 = 6, Youth State League 17 = 7, 15 = 8; teams in the same division share a number; 0 means not set (never suggested). Stored with the team's other settings, so a new season inherits it.
- "Load default club team list" resets the *selected season's* list to the club defaults; other seasons are untouched.
- **Create season** (button beside the Configuration season selector): registers the next season (highest known + 1, e.g. 2028) so it appears in every season selector before any data exists, and **copies the previous season's team list** into it as a starting point — ready for season dates, fee matrix, and trial opening.
- Upgrading from a pre-1.48 global list is automatic: every season with data (plus this year and next) receives its own copy of the old list, and the old list stays behind as the fallback for any season never seeded. The trial form shows each open season its own teams and switches lists when the applicant changes season.

### Trials

Front-end form via `[team_trial_form]` (login required; prompts to log in / create an account with an explanation):

- **Prefilled, read-only account details** (name, email, phone, DOB, gender, institution) — edited via the profile, never the form. Submission requires only what trials genuinely need: name, contact number, DOB and gender (age rules + competition). MUS/degree fields are **not** required to apply — they're a fee-class matter, collected by the annual profile wall and resolved at invoicing.
- Competition (men's/women's) derives from profile gender; the question is only asked when the profile can't answer (unset/non-binary). The team list leads with the applicant's own competition, so a women's-competition player sees Women's Teams first rather than scrolling past a greyed-out men's block. Within each group teams appear in the same natural code order as the Configuration page, and once eligibility is worked out (competition + age rule) the teams they can't pick sink to the bottom of the group, so what they *can* apply for is always at the top.
- Questionnaire mirrors the club's VVL trials form: VVL history (with conditional returning-player and club-transfer sections — the previous club is a dropdown of the VVL clubs plus Other Victorian / Interstate / International options that reveal a club-name field, stored as e.g. "Interstate: Sydney Uni"), international player details, team selection (real teams, grouped by gender, with ineligible teams greyed out live by competition and DOB cutoff — enforced server-side too), positions, venue availability, trial-date availability, experience. Answers stored as JSON (`form_data`).
- **Missing tick-box answers**: teams, positions and venues are tick-box groups the browser can't enforce, so the server names the one that's missing (Pick at least one team / position; for venues it points at the I can train at all venues option) rather than a generic required-fields error.
- **Per-season opening**: "Accepting trial applications for: [year checkboxes]" (Trial Applications → settings). Only ticked seasons appear in the trial form's season selector, and submissions for unticked seasons are rejected server-side; with nothing ticked the form shows a friendly closed notice. The status panel (trial number, confirmed / awaiting payment / assigned — an assigned player sees team names only, never codes: a multi-team finalisation reads A and B, and Training Only teams are marked (training only)) is about **one season only** — the latest open season, or when nothing is open the newest season anyone has applied for — so last season's "your 2026 application is confirmed" never lingers once 2027 opens. The settings summary shows the open seasons, or APPLICATIONS CLOSED in red.
- **Trial fee rules** (Configuration → Trial application rules): who pays the trial fee is an if-then rule set — by default **new-to-VVL and transferring players pay**, **returning Renegades players are free**, and **anyone under 18 is free regardless** (threshold configurable, 0 disables). Waived applications submit directly (no checkout) and record the waiver reason in the application ("Waived — under 18" / "Waived — returning Renegades player"). The form's fee notice adapts: juniors see "trials are free for players under X", adults see who the fee applies to. The **transfer club list** is editable in the same section (one club per line; empty = built-in VVL default list).
- **Trial fee**: configure a product in the Trial Applications settings box. Submissions save as `awaiting_payment`, go to checkout, and become reviewable (`pending`) when the order is paid. Unpaid applications stay `awaiting_payment` until paid (they no longer expire); "Mark as Paid" covers offline payments. No fee product = direct submission.
- **Refunded or cancelled trial fees**: refunding a paid trial fee in WooCommerce (fully or partly), or cancelling the order after it paid, doesn't change the application, which still counts as paid. Each refund (or cancellation) is logged once as *Trial fee refunded or cancelled* on VVL Oversight → Logs, naming the order, the amount, the season and the trial number. The last 30 days of them are listed in a warning at the top of Trial Applications so an admin can follow up anyone who should still pay; each stays listed for the 30 days, followed up or not. Unpaid orders that get cancelled raise nothing.
- **Who pays** (Configuration → Trial application rules — four independent toggles): new to VVL ✓, transferring from another club ✓, **played for Renegades last season** ✗ (their yearly membership already covers it), **Renegades history but sat a season out** ✓ (no current membership, so they pay like anyone else). The last two were one rule before 1.51.0, which wrongly waived lapsed players.
- **Waive fee** (Trial Applications, on any unpaid application, next to Mark as Paid): for when the club decides someone shouldn't pay — typically a last-season player who ticked the wrong history option. A reason is required; the application moves to the review queue, the Trial Fee reads "Waived by club — *reason* (*admin*, *date*)" (the reason is for admins only, as the form says — coaches see just "Waived by club"), it's logged in VVL Oversight → Logs, and the player gets the *Application received* confirmation (not a payment receipt — nothing was paid). The waiver **sticks**: if the player edits their application later, the fee is not re-assessed. Use Mark as Paid only when money actually changed hands outside the site.
- The history options are mutually exclusive: "played for Renegades **last season**" (free) versus "played for Renegades before, **but not last season**" (pays by default). The second option's old wording was also true of last-season players, who sometimes picked it.
- **Junior exemption**: free under a configurable age (default 18) — but *only when every team they pick is Youth State League* (U/17 or U/15). A junior reaching up to JPL or a senior team pays. The form spells this out to under-age applicants, and the rule is enforced server-side from the teams actually submitted.
- **Unpaid applications** show a **red** status panel with a direct **Pay the trial fee** button rather than asking the applicant to fill the form in again. The link is nonced and bound to the application: it rebuilds the cart line and goes straight to checkout, and does nothing for anyone but the owner of a genuinely unpaid application.
- **After saving**: when no payment is needed, submitting or saving changes reloads the rego page itself, back at the **top of the page** (the browser's usual "restore where you were" is switched off for that reload, so they don't land back down by the Save button) — green status panel with the trial number, the form ready for more edits — with a one-off notice on top ("Thanks — your application has been submitted" / "Your changes have been saved"). When the fee is due it goes straight to checkout instead.
- **Editing after submitting**: coming back to the form reopens the application with every answer filled in ("Edit your trial application" / **Save changes**), until the season's applications close or a team is assigned. It is the same application — same trial number, coach verdicts and notes kept — and the edit is stamped **Last Edited** on the application so coaches can see it changed. Answers are rebuilt from the stored snapshot, so applications submitted before this feature are editable too. Fees are re-assessed on edit: **paid stays paid** (online or Mark as Paid — never charged twice), but a waived application edited into a paying category (e.g. switching to a club transfer, or a junior adding a senior team) becomes due and goes to checkout, closing the "apply free, then edit" gap. The 7-day unpaid expiry counts from the latest edit (`updated_date`), not first submission. Assigned (accepted) applications are locked with a "contact the club" note — which also fixes an old gap where submitting again after acceptance created a duplicate application with a new trial number.
- **One application per account per season**, even under a double-tap: saves for a season are serialised with a database lock, so two requests arriving together can't both see "no application yet" and create two (the second waits, then edits the first). The same lock stops two different players being handed the same trial number. The Submit button also locks while sending ("Sending…") and unlocks if the save fails.
- **Trial numbers**: per-season sequential number assigned at submission, shown persistently to the player (status panel on the form page), on the checkout trial-fee line (Trial number #N — the internal application id is never shown) and throughout admin/coach views — players can write it on themselves at busy trials. Numbers are never reused: the plugin remembers the highest number handed out each season, so deleting the newest application doesn't pass its number to the next applicant (an older printed trial book can't point at the wrong player).
- Optional **training-info page URL** linked at the top of the form so players pick teams by training venue/day.

### Coach portal

`[team_coach_portal]` — visible only to logged-in users with an active coach/assistant-coach assignment or committee access; each coach sees only their own teams (server-enforced). Mobile-friendly card layout: each card's controls sit in two rows, the verdict and the offer controls (editors only) and then the expanders (Emergency contact, Application, Notes, Attendance) with **Mark attended** at the right end, in the same place on every card; on a phone they stack full width, with Mark attended above the expanders. A confirmed player's card is the team list instead (see below). Coaching a season opens it until that season's team memberships run out — **1 April the following year** — so last season stays reachable while the next teams are picked, then closes: a former coach no longer sees old applicants' contact and emergency details (committee access is separate and unaffected).

- **Committee access** (VVL Oversight → **Committee Access**): club officials can open **every team** in the portal, picked from a team dropdown (teams they coach listed first, each group in team-code order, as on the Configuration page). **Edit all teams** gives a coach's powers on every team (verdicts — labelled *Team verdict* — attendance, notes); **View all teams** is read only: the cards, applications, notes, attendance history and trial book are all visible, but no verdict, attendance or note controls are shown and the server refuses those actions. Site admins always have edit access. A coach with view access still edits the teams they coach. Grants are made by email or username, can be changed or removed, and every change is logged.

- **Team switcher** for multi-team coaches; **Coaching Staff** table + **Players** cards (confirmed members plus selection-board players, tinted by verdict, over-age players flagged with DOB and "VV exemption required"). Selection-board players keep the applicant card format: trial number, registration-status chip, and the expander row (emergency contact / application details / shared notes with add-note / attendance) with Mark attended. ### Fees & Payment Management

Fees are a **balance against a season timeline**, not an invoice event:

- **Season dates** (Configuration, per season) drive everything. No dates = full fees, nothing overdue.
- **Fee matrix** (Configuration, per season): rate per fee class × role, edited as a **grid** — one row per fee class, three columns: playing member, training only, supporter (coaches pay the supporter amount, team managers the playing member amount). Blank cells have no fee set and can be filled in; a season with no fees starts as an empty grid, with a button to **copy another season's amounts** as a starting point. Configuration lists any blank cell someone can actually fall into (every class except Unknown). This matters because a person with several roles is charged the highest role that *has* an amount. A blank playing-member cell would charge a player who also coaches only the supporter amount, and someone whose roles are all blank isn't invoiced. Every standard fee class always has a row in the grid, so a class missing from the matrix can be filled in. **From 2027 every cell has two amounts** (1.76.0): the *Fee* (leave it blank until it is known in January) and the *Limit*, the upper limit the club guarantees the fee will not exceed. Offers sent before the season's fees are released are quoted on the limit; a fee above its limit is saved with a warning (players quoted on the limit are capped at what they were quoted), and the Configuration page lists in red any cell offers can land in that has no limit. Copying a season into a 2027+ season copies the limits and leaves the fees blank (tick boxes copy the fees too, or start the limits from last season's fees); a second copy never overwrites a limit typed since. Every fee and limit change is logged. A fee can be cleared again (blank) while the season's fees are not released and it has no invoices.
- **How a season fee is worked out** (1.66.0): every team someone is on is a *bucket* — team + role + fee class, where the class can differ per team (an under-19 pays JPL/YSL rates on a junior-league team and Junior U/19 (VVL) rates elsewhere). (1) Each bucket is priced from the matrix — playing member, training only and supporter at their own amounts; **coach and assistant coach at the supporter amount**, **team manager at the playing member amount** (the matrix only has those three columns). (2) The fee is the **highest bucket** — buckets never add up, and there's **no coaching discount** (handled outside this system), so someone who only coaches pays the supporter fee. (3) **Pro-rata per stretch**: the fee history records the buckets for each stretch of the season, each stretch is charged for its share of the season dates, and the stretches add up — so a mid-season upgrade or a late start is charged exactly. For 2026 and earlier the stretches come from the fee history (fee segments, below); from 2027 they come from each team place's own start and stop dates (see Fee timeline, below). Payment Management shows this working in a **"How it's worked out"** dropdown on every invoice (buckets with what each is charged as, the highest fee, pro-rata, total) and flags any invoice that no longer matches the calculation.
- **Fee class** (from the 2027 season): the moment the class is judged at is fixed for the season, so the day the fee happens to be worked out never matters and time passing never moves anyone between classes. **Junior** (Junior U/19 (VVL), or JPL/YSL on a junior-league team) follows Volleyball Victoria's U19 date-of-birth cutoff for the season being priced: born on or after 1 January of (season − 18), i.e. no 19th birthday during the season. This is the same cutoff as the U19 team age rule, so it rolls over with the season. **Alumni** (degree ended, so Full Adult) is judged as at the moment the person's fee was first recorded for that season: the first entry in their fee class history, made when Finalise, Accept or Add Assignment first puts them on a team (for a 2027 fee first recorded before 1.70.1, their first fee-history entry still counts). A backdated start doesn't move that moment; removing every place they hold that season as *added by mistake* restarts the history, so a later re-add is judged afresh. So a degree that ends mid-season changes nothing that season. The profile is still read whenever the fee is worked out, so a later profile change (institution, staff, degree end date, e.g. at the annual profile update) changes the class from the day the next re-price picks it up, and the fee splits there; earlier days are never re-priced. 2026 and earlier seasons keep the original rule (age and degree end on the day the fee is worked out), so they price exactly as they always have. The team view's MUS Category column and Payment Management's fee-info line follow the season's rule too: from 2027 Payment Management shows *U19 in 2027* or *not U19 in 2027* instead of an age, and judges Alumni at the same moment as the fee.
- **Fee release date** (Configuration, per season, beside the season dates): people can be put on next season's teams before its fees are known. Until the release date **nobody is invoiced** for that season (their fee-role history is still recorded); on the date, a daily check invoices everyone on a team at once, and anyone added afterwards is invoiced straight away. **Release fees now** does it immediately, and so does clearing a release date that hasn't been applied yet (the page asks first; everyone already on a team is invoiced, with the same counts; clearing a date that was already applied just removes it, re-pricing nothing). **A season already being charged is never re-priced by saving or clearing its release date.** That means a season whose release was applied, that had no release date, or that was moved to a future date with its invoices still out (some at a real amount, none taken back to $0 by Remove fees until release; only automatic invoices count, since a fee set with Edit Fee stays through both). Saving a date that has passed, or clearing the date, then keeps every existing invoice as it is, and only people on a team with no invoice yet are invoiced. A future date saved by mistake can be put right by saving the old date again. Moving a charged season to a future date re-arms the release: on that date, or with Release fees now, its invoices are re-priced from the fee matrix (except fees set with Edit Fee, which no release ever re-prices), and the save notice says so. Once fees have been taken back with Remove fees until release, a passed date is a real release and re-prices everyone. Release notices (Release fees now, a passed date, clearing an unapplied date) and the daily release log line also list two groups. **Partly priced**: a role with no amount in the matrix, so charged the highest of their roles that has one. **Not priced**: an existing invoice left as it was because none of their roles has an amount, so a $0 credit invoice stays $0; these aren't counted as re-priced. An admin then fills in the matrix and corrects the fee: their next team change re-prices it, or Edit Fee sets it (it then stays as set; Use calculated fee puts it back to automatic). **Manual fees kept**: fees set with Edit Fee, left as they were (not counted as re-priced either). People with no fee at all are invoiced by saving a passed release date again. Pro-rata still runs from the season start/end, not the release date, so people added before the season starts pay the full season (from 2027, any place whose start date is on or before the season start). No release date = fees are charged as people are added (the original behaviour). Before release nothing is charged or re-priced, even when someone's teams change. Invoices issued before a release date was set can be taken back with **Remove fees until release**: unpaid ones are deleted; ones with payments drop to $0 and the money shows as **credit** (the payments ledger is never touched), then on release they're re-priced to the real fee with the credit taken off. A fee set with Edit Fee is kept as it is (the notice counts these); to take one back too, use Use calculated fee on it first. The *issued before the release date was set* warning, the button and its confirm count automatic invoices only, so they go once those are taken back, and fees set with Edit Fee get a line of their own saying they stay through the release. Releases, removals and date changes are logged.
- **Fee segments** (`team_fee_segments`, 2026 and earlier): a dated history of each member's fee role per season. From 2027 nothing writes or reads them, because the fee follows each team place's own dates (see Fee timeline); 2027 segments recorded before 1.70.1 are left as they are. Every assignment change (accept, finalise, role edit, delete, set Inactive) checkpoints it; the season fee is the sum of each segment's rate × its share of the season window. So joining mid-season pro-rates, upgrading training-only → playing mid-season charges each period at its own rate, becoming a coach mid-season applies the coach rate from that date, and leaving all teams freezes the fee at the accrued amount — **$0 when they leave before the season starts**, whatever the fee matrix says (anything already paid shows as credit, and the change is logged; invoices with no fee history keep their amount, and so, mid-season, do roles missing from the fee matrix). Someone whose email changed is judged by their account as a whole, so removing a row under an old email never drops the fee of someone still on a team (deleting a row on Team Assignments re-prices the person under their account's current email, so their other teams still count). Segments clamp to the season window, so anything effective before the season start charges from the start. Coming back onto a team after leaving every team never charges twice or charges the time they were off: the new stretch starts that day, or at the new assignment's start date when that falls after they left (a deliberate backdated re-add). Payments already made always carry forward (outstanding = new fee − paid).
- **Payment schedule**: for 2026 and earlier, fees fall due linearly between the season dates; from 2027 each player's fee falls due across their own part of the payment window (see Fee timeline, below). Overdue = due by today − paid, never more than what's outstanding. Members see a breakdown (season fee / paid / remaining / overdue, plus *Due by today* from 2027), a "Next payment due" date when on-track, and a progress bar (paid % against season % elapsed, or from 2027 against the share due by today). **Past-season debts roll forward**: once a season's year is over, whatever remains outstanding counts as fully overdue (season dates or not) everywhere overdue is shown, and payments always clear the oldest season first.
- **Fee standing and the one-month flag** (1.69.0, club decision): how far someone is behind is measured in time, not dollars: from the date their payments last covered on the schedule to today, across all their invoices (an earlier season's leftover is behind from that season's end, as for the reminder emails). Behind means at least $1 overdue. **A month (30 days) or more behind flags them as not to train**, on the coach portal's team list and on Payment Management. Two rules keep the clock fair. A fee is never behind from before it was billed: the later of the invoice being created and the fee last being raised (by a re-price or Edit Fee). So a player joining mid-season on a pro-rated fee, fees released after the season starts, or a fee raised mid-season (say training only to playing) count from that day, and are flagged only if a month then passes without their payments catching up with the schedule. Paying something isn't enough: for 2026 and earlier the schedule still runs from the season start, so from that day it already expects the share of the fee for the season so far. From 2027 (1.70.2) each player is measured against their own schedule, and the clock never starts before the latest of: the fee being billed, its last rise, the latest recorded change that put more money due on the day it was recorded (a backdated start, a stop recorded late, a role upgrade), and the payment window being moved earlier. So a player added on 21 Oct with a start of 1 Jun counts as behind only from 21 Oct and can't be flagged before 20 Nov, and a change that lowers what's due never moves the clock. A lower fee or a re-save doesn't restart the clock. Every rise does, even back up to an amount held before (taken off a team and put back): where the rule can't be exact it errs towards not flagging someone, never towards flagging a player who has just come back. And only an invoice at least $1 overdue sets the date, so cents left on an old season can't make a fresh debt look months old (when only small amounts add up to $1, those seasons are named). An invoice with an account only ever counts for that account, so someone now using an email that once belonged to another member's account never gets that member's fees; an old invoice with no account still goes by its email. An admin can record a **payment arrangement** (Payment Management → *Arrangement* on any of the person's rows, with a note of the terms that only admins see). It covers everything they owe at the time, every season. Those invoices still count as behind, but never towards the flag, and their coaches see *payment arrangement* instead. *End arrangement* clears it from all of them. A fee issued later (next season, say) or raised since isn't covered until the arrangement is recorded again: *Extend arrangement* on that row does it, keeping the terms (*End arrangement* sits beside it). Arrangements are logged (*Payment arrangement* on VVL Oversight → Logs). They don't change the overdue reminder emails. `TeamOversight_Payments::get_fee_standings()` is the one place this is worked out.
- **Fee timeline (2027 season on, 1.70.1; personal due dates 1.70.2)**: each team place has its own start date (charged from that day) and stop date (the first day off the team, not charged; blank = still on), set only by admins, and the fee follows those dates. For each day inside the season dates the player is charged the highest rate among the places they hold that day; places never add up. For example, in a 1 Feb–30 Nov season (302 days charged) with playing $1,000 and training only $500, training only from 1 Feb plus playing from 1 Apr is 59/302 × $500 + 243/302 × $1,000 = **$902.32**. Days before the season start or after its end aren't charged. Late news is normal: backdate a start or a stop and the fee re-prices to the real dates straight away (once fees are released); anything overpaid shows as credit, and payments are never changed. 2026 and earlier seasons charge exactly as before.
  - **Placing people**: Finalise Coach Selections (one date per run), Accept, bulk accept and Add Assignment each take a start date, defaulting to today. A start after the season's **late-join cutoff** (*Paid in full by*) is refused with the reason, and nothing is written: Finalise checks before it inserts anything, bulk accept before it starts. A start before 1 January of the year before the season (a typo in the year) is refused too. With no season dates there is no cutoff, and the forms say so. A team someone already holds is left as it is, so re-running Finalise or bulk accept never adds a place twice.
  - **Changing places** happens on the person's **Fee timeline** card on Member Lookup (above), opened from their name on Payment Management or the *Fee timeline* button on Team Assignments. **Stopped playing on** keeps the place and its history and charges up to the day before; **Remove (added by mistake)** charges nothing for that place; **Change role or team from [date]** stops one place and starts the other. A future stop keeps them on the roster until that day, when the daily job takes the place off (and, for a playing place, drops that team's Selected verdict to Tentative). Every change goes in the change history with who made it, when, and the fee before and after.
  - **Team Assignments** shows 2027-and-later rows read-only (team, role, dates, status), each with a *Fee timeline* button, and the server refuses edits and deletes of those rows. 2026 and earlier rows edit as before.
  - **Undo Assignment** in 2027 and later removes the playing places as added by mistake (see Undo Assignment, above).
  - **Configuration**: for a 2027-or-later season the Season Dates box becomes **Season dates and payment window**: season start and end (what fees cover), plus **Fees due from** and **Paid in full by** (blank uses the season start or end; Paid in full by is also the late-join cutoff). The dates must run season start ≤ Fees due from < Paid in full by ≤ season end, and a season-date change that would leave a saved window outside the season is refused unless the window is fixed in the same save. Changing the season start or end re-prices every automatic invoice for the season straight away, once fees are released (the page asks first; fees set with Edit Fee are kept and listed; the counts are shown). Changing only the payment window re-prices nothing, but what everyone has due follows the new window straight away (moving it earlier never makes anyone count as behind from before the save). Places that now start after the cutoff are listed, not changed. Every save is logged with the old and new values (*Season dates / payment window* on VVL Oversight → Logs).
  - **Releases**: before the release date places and changes are saved and nothing is billed. On release everyone is priced at their real dates, including players who stopped before it. Someone whose places all fall outside the season dates has nothing to pay and is skipped quietly, not reported as a fee that couldn't be worked out.
  - **Due dates (1.70.2)**: each player's fee falls due evenly, day by day, from the later of *Fees due from* and their first start to *Paid in full by* (all on their start day for a legacy start on or after it). Nothing is due before then, and once every place has stopped, everything for the time played is due at once, even before the window opens. A fee set with Edit Fee is spread the same way. Due amounts move at midnight site time, so the amount shown and the amount charged agree all day. Member fees, `[player_fees]`, the pay box (it charges what it shows), Ready to Play, the reminder emails, the fee standing and no-training flag, Payment Management's Overdue column, Member Lookup's Fees card, the dashboard and the Fee timeline card all use it; 2026 and earlier keep the season-long schedule unchanged. Saving a new payment window changes what everyone has due straight away and re-prices nothing; moving it earlier never makes anyone count as behind from before the save. In the worked example (window 1 Apr–1 Aug), a full-season $1,000 player has $500 due on 1 Jun, a 1 Jun joiner ($602.65) has $296.39 due on 1 Jul, and a February-only player owes all $92.72 from 1 Mar.
- **The payments ledger is the single source of truth for money.** Paid = the sum of `team_invoice_payments` rows for the invoice; outstanding = fee − paid, always computed, never edited. Every dollar — online, cash, EFT, corrections — is a ledger row with a date, source, and note. (A one-time migration backfilled `reconciliation` rows for payments recorded before this model.)
- **Pay-any-amount**: `[member_fees]` (and the Ready to Play fees step) let members pay whatever they choose whenever they like via a dedicated payment product whose price is overridden to the chosen amount. The pay box asks explicitly — **pay what's overdue** / **pay the full balance** / **pay a different amount** — each option showing its figure, the custom field left empty (a prefilled amount used to read as fixed), and the button naming exactly what it will charge ("Pay $150.00 now"). The choice is resolved server-side, so it holds without JavaScript, and overpayments are still capped at the balance. Paid orders apply oldest season first, each application recorded as an `online` ledger row: the first carries the order item, which stops the processing and completed hooks from applying it twice, and the rest carry the order number with a "Part n of m of order item #X" note. Anything paid above the balance (e.g. a cart left over from before a cash payment or fee change) is recorded on the newest invoice as an "Overpayment" row, so it shows as in credit for the treasurer to offset or refund. A payment that can't be recorded (no invoice at all, or a part that fails to save) is logged as **Unapplied payment** on VVL Oversight → Logs with the order number and amount, for the treasurer to record with Record Payment or refund. The payment product is sold individually (quantity is always 1).
- **Refunds and cancellations**: a fee payment refunded in WooCommerce (fully or partly, including setting the order to Refunded) or cancelled after it was recorded never changes the ledger by itself; a refund is still a negative **Record Payment**. Each refund, and each cancellation, is logged once as *Payment refunded or cancelled* on VVL Oversight → Logs, naming the order, the amount refunded and what the order paid on each season. The last 30 days of them are listed in a warning at the top of Payment Management so the treasurer can put each one right; an entry stays listed for the 30 days even after it has been put right. Put the order number in the Record Payment note (for example *Refund order #123*): the note shows on Logs and Member Lookup, which is how to check a refund has already been entered. A refund entered as just an amount on an order that also held other products is flagged to check how much of it was the fee. A refund or cancellation of a payment that was logged as unapplied says the plugin never recorded it: record only what the club kept, or, if it has since been recorded by hand, a negative payment to match. Orders that never reached the books (an unpaid order cancelled by the stock-hold timeout) raise nothing.
- **Payment Management** (admin): one row per member per season — fee, paid (from the ledger, with the percentage of the fee), outstanding, overdue, payment count (hover for the ledger detail). For a 2027-or-later season the Overdue column is each player's own schedule, and the caption says how that season's fees fall due (*Fees cover [season dates]; they fall due from each player's start (not before [Fees due from]) to [Paid in full by]; a player who stops owes the rest at once*). On a 2027-or-later row the name opens that person's Fee timeline for the season on Member Lookup (no link when neither the invoice nor its email belongs to an account). Under Overdue, how long they've been behind across all their seasons (*3 weeks behind*, or *2025 fees a month behind* when only an earlier season is late), a red **No training** badge when they're a month or more behind, and a blue **Arrangement** badge (hover for the terms, who recorded it and when). A notice at the top names everyone flagged, including players on a team that season who have no fee for it yet but are flagged for an earlier season's fees. A **Schedule** filter shows those behind, a month or more behind, or with an arrangement. **Arrangement** / **End arrangement** on each row records or ends a payment arrangement (see Fee standing, above). The arrangement is the person's, so its badge and the filter show on every season's row; a row whose fee it doesn't cover yet offers **Extend arrangement** instead. **Edit Fee** sets the fee by hand (payments are untouched; outstanding recomputes), and **a fee set this way sticks** (club decision, 1.68.5): no automatic re-price changes it. That covers team changes on Team Assignments and on the Fee timeline (Remove included), Accept, Finalise, Undo Assignment, a 2027-or-later season-date change, Release fees now, the daily release, a re-armed or re-saved release date and Remove fees until release. The fee history is still recorded as usual, and whenever a re-price would have set a different amount, Logs gets one *Manual fee kept* entry with that calculated amount (once per amount, so it doesn't repeat). The row shows **Manual fee · calculated $X** (hover for who set it and when), and the breakdown explains the difference. **Use calculated fee** puts it back to automatic and re-prices it from the fee history and matrix straight away (logged; payments stay, outstanding = fee − paid). Editing the fee again keeps it manual. Someone with a manual fee who leaves every team keeps it: their row says *On no team now*, and a warning at the top of the page lists them, so the treasurer can decide (Use calculated fee drops it to $0 if they left before the season started, or to what accrued). Nothing re-prices it silently. Existing invoices from before 1.68.5 all start automatic (the old Edit Fee left no mark that could be backfilled safely), so a fee set by hand before then must be saved again with Edit Fee to stick; until then a team change, Finalise of that player or a real release re-prices it as before. Logs, searched for *season fee changed from*, finds them. **Record Payment** adds a `manual` ledger row for cash/EFT/corrections (negative amounts allowed for refunds), stamped with who recorded it. If it can't, it says whether the invoice no longer exists or the save failed with nothing recorded (reload and check before trying again). Outstanding itself is not editable — by design. Every re-price of an existing invoice (a team change, Finalise, a release, Use calculated fee) is logged on VVL Oversight → Logs with the old and new amounts. The breakdown's summary line flags **⚠ partly priced** (a role with no matrix amount was left out, so the fee may be too low) or **⚠ no matrix amount**.
- **Overdue reminder emails**: optional (off by default), managed on **VVL Oversight → Emails**: editable subject, heading and message with placeholders (`{first_name}` `{name}` `{overdue}` `{outstanding}` `{time_overdue}` `{days_overdue}` `{link}`), `{fees}` for the person's fee cards (one per season with money owing: season fee, paid so far, remaining, overdue now or the next payment date, and the Player Checklist's progress bar, every figure from `invoice_schedule()`, as at the day it's sent) and `{button}` for the Pay button (see *Club emails*, below), configurable From name/address + Reply-To (the From address must be one the site's mail account may send as, or the mail service swaps in its own; Reply-To can be any real mailbox), a live preview with a made-up member, "Send test email to me", the automatic-send switch, per-person interval (default 7 days), a **grace period** before anyone is emailed (default **7 days behind**, plus a token $1 floor). Fees fall due gradually, so everyone tips a few dollars overdue almost immediately — gating on *how long* someone has been behind rather than *how much* means small-but-genuine debts still get chased, while nobody is emailed the day the schedule ticks over. "Behind since" is computed from the payment schedule (the date the accrual overtook what they'd paid; from 2027 on the player's own schedule, and never before the fee, or the change that put more due, was recorded, so the grace period counts from then); past-season debt counts from the season end. The email says how long: "behind the payment schedule for 2 weeks". Both gates are email-only — members always see their exact figure on site, **send time + timezone** (default **6:00pm Australia/Melbourne**; the page shows the next scheduled run and the cron re-anchors itself whenever the setting or DST moves it), "Preview recipients" (lists who would be emailed without sending) and "Send reminders now". The daily check covers rolled-over past-season debts; only people resolvable to a WP account are emailed (trials are account-gated, so that's everyone with a fee).

### Ready to Play

`[ready_to_play]` — shows the checklist for people on a team (an active team assignment, i.e. once the club has run Finalise) for the current or next season. A coach verdict never shows here, and neither does a sent offer on its own: "You're in: *team*" appears once the player holds an active team place (from 2027, that is once they lock in and the club places them). An offer that has been **sent to the player** (2027 on) puts a banner above the panels that says where it is up to, links to the offer page and, once they have accepted, holds the deposit step with its pay box; the offer page previews the offered team's requirements read-only. **Once the player accepts** (club decision, 28 Oct 2026: the checklist is there from acceptance, so they can see what kit they need), that season's panel is the full player checklist with the offered team counted (`compute()`'s `$extra_teams`, the same path as the preview), ticks and all, alongside any team they really hold ("You're in") and any team they coach ("You're coaching"). Its heading never says they are on that team: it says they have accepted a place and must pay the deposit to lock it in (or, once the deposit is complete and before the club places them, that they are locked in and being added), and its fees step is the deposit, a link to the deposit box in the banner above, with no pay box or amount of its own (money owed elsewhere still shows with the usual pay box). The wording is in the offer wording registry. A sent offer, a coach verdict alone and every ended offer (declined, withdrawn, moved to declined, not approved, cancelled, left) count for nothing; seasons before 2027 ignore offers. Anyone logged in who *isn't* selected sees the fee panel instead, so ex-players carrying a debt can still see and pay it. Members with **no fee record at all** see nothing: the plugin deliberately never says "you have no outstanding fees", because legacy fees can exist outside this system and implying someone is square would be wrong. (Logged-out visitors also see nothing.) Team managers count as players (their role only exists for the fee discount). Coaches/assistant coaches who aren't also playing get a reduced "Get Ready to Coach" checklist: VV registration + fees only, no kit steps. Player steps in priority order:

1. **VV membership** — external registration link + manual tick.
2. **Playing shirt payment** — the club issues the shirt; the payment is once-ever, so **all-time** purchases of the configured shirt products count, no self-tick, and admins can record a **credit** (with note) for shirts paid under a different account. Quantity from the team config.
3. **Shorts & socks** — regular products: this-season purchases auto-complete, manual tick for older kit, shop link always available for re-orders.
4. **Fees** — breakdown across **all seasons** (carried-over debts surface here as overdue), schedule status for the panel's season (from 2027 on the player's own schedule, with their window in the wording), and the pay box (live when the payment product is configured; it charges the overdue figure shown). Until the panel season's fees are released, its invoice with nothing owing (a $0 placeholder, or an early payment held as credit) isn't counted: the step says the fee hasn't been released yet and when it will appear (the release date), and mentions any amount already paid towards it, instead of "Paid in full" with $0 figures. It shows in orange (numbered, not ticked) so players know to come back, and with everything else done the banner reads *All done for now — just your fee to come once it's released*; it still counts as done, so the admin Ready flag is unchanged (Player Readiness shows *Fee not released yet*). `[member_fees]` does the same for each such season's card. A fee set by hand before the release still shows as usual.

Admin: VVL Oversight → **Player Readiness** — every selected player's VV/shirt/kit/fees status and a Ready flag (coach Selected / Training Only verdicts count here before Finalise, so kit can be planned early), plus the settings (URLs and kit product IDs) and per-player shirt credits. Each player appears once, evaluated for the **latest season they're in** (current year or later) — so end-of-year selections for next season show next-season readiness immediately.

### Running offers: a guide for the committee

This section is for whoever runs offers this season, whether or not they have touched the website before. The same guide, with this season's live figures in it, is on VVL Oversight → **How it works** → *Offers and deposits*. The technical rules follow in the next section.

**In plain English.** From the 2027 season a coach's selection becomes a place through an **offer**. The coach asks for an offer, an administrator approves it, the website emails the player, the player accepts or declines on the website, and they **lock in** their place by paying a **deposit** (a small share of the season fee) in one payment. The moment the deposit is complete they are put on the team automatically. An offer sent before the season's fees are released is an **Early Offer**: it is quoted on the fee matrix's **upper limit** (the most the fee can be), the real fee is set later and is never more than that limit, and the deposit comes off the final fee. Nothing is released automatically: when a date is missed the coach (or an administrator) decides what happens.

**The committee runbook**

1. **Before internal trials: get it ready (an administrator).** Open the Offers page's *Setup* tab (or Configuration → *Offers and deposits*). The **setup checklist** reads everything live and marks each row *Ready*, *Check* or *Fix*, with a link to the screen that fixes it: season dates, the fee release date, an upper limit in every fee cell, a division level on every team, the offer settings, the pages the offers link to, the deposit payment product, the permission to send offer emails, a coach on every team, who can approve, the daily check. It never blocks anything.
2. **Make the numbers yours (an administrator).** On Configuration → *Offers and deposits* check the four offer settings (reply within 7 days; pay the deposit within 14 days but not before 10 January; deposit 10%) and press Save even if you change nothing: that records that a person has checked them. The worked example under the form shows the dates an offer approved today would get.
3. **Read the words (an administrator).** Under Emails → *Offers and selection* read the offer emails, the commitments and deposit policy and the *Offer wording* panel (the Early Offer explanation, the money policy, the lines on the offer page, the coach portal's flow chart). Every line has the built-in text beside it and a way to put it back. Press *Send a test of each switched-on offer email to me* and read them in a real inbox.
4. **Give the permission before the first approval (an administrator, on the live website only).** Emails → *Offers and selection* → **Allow this website to send offer emails**. There is no offers on/off switch (1.79.0): from 2027 offers are how selection works, and this permission and the committee's approval of every offer are the two controls. Give it before anyone approves an offer: approving is what starts an offer (its reply-by and deposit dates run from that day and the player can see it on their own pages), and only the email waits for the permission, so an offer approved without it loses days before the player hears about it (1.79.1: the *To approve* tab and the Approve confirms warn while the permission is closed). The permission belongs to the website's address, so a test copy of the website can never email players, and it is lost if the address changes (see *Holding things back*). Nobody is ever sent a "not selected" email by the website on its own (1.80.0): Offers → *Not selected* lists every player a team has turned down, for a team they applied for and with their application still open, whom nobody has told, players turned down before offers began included.
5. **Coaches select and send (coaches).** Selected or Training Only, then *Send offer* (or *Send offers to all*). Nothing is emailed. The coach can cancel while it waits. A Rejected player is told nothing until the coach presses *Send "not selected" email* on their card (or *Send "not selected" emails* for the board); that email is about the coach's team only, replies come to that coach, every coach of the team is copied (that coach included), and the coach can send it while other teams are still deciding.
6. **Approve every day (an administrator).** VVL Oversight → **Offers** → *To approve*. Check each row (the quote, "Also holds", "Earlier balance"), then Approve (the player is emailed and the team's coaches are copied) or Decline (the coach sees *Not approved* and the player is told nothing). The page header lists anything that *Needs attention*.
7. **Watch the replies (an administrator).** *Waiting on players* lists offers waiting for a reply (*Offer sent*) or for the deposit (*Accepted*), overdue ones first. *Remind* emails the player again; *+7 days* and *Move to declined* email nobody; *Withdraw* emails the player.
8. **Check placements (an administrator).** *Locked in* lists players whose deposit is complete. Anyone shown *Not placed* has a reason; press *Retry placement*. A player who pulls out: *Player pulled out* (nobody is emailed: speak to them yourself).
9. **Settle the money (the treasurer, who needs an Administrator account).** *Held deposits* lists deposit money that is not on a live offer. Most deposits are settled by the site the moment the offer ends: a withdrawal by the club holds it as credit to refund (refund it from Payment Management with a negative Record Payment), and a decline or a move to Declined keeps it (the *Forfeited* list on the same tab; *Reverse forfeit* gives it back). Only a few wait for a decision (a place removed outside the Offers page, a reversed forfeit, money the site could not settle): mark those *Refund owed* (the club broke its side) or *Club keeps it* (the player broke theirs).
10. **At fee release (an administrator).** Offers quoted on the limit drop to the real fee automatically if it is lower, and nobody is invoiced above what they were quoted. Look at *Locked in* and *Held deposits* once more.

**When something changes after the offer is out**

- *A player pulls out after locking in.* Offers → *Locked in* → **Player pulled out**, choosing who broke the commitment. The place comes off the team first, then the offer ends. Nobody is emailed. If the player broke it, the deposit is kept; if the club did, it stays as credit to refund.
- *The club withdraws an offer.* **Withdraw**: the player gets a short email and the coach can then change the verdict. A deposit already paid is the player's to have back, so it appears on *Held deposits* as credit. A coach can withdraw an offer nothing has been paid on; once money is held only an administrator can.
- *A player pays and nothing happens.* *Locked in* shows *Not placed* with a reason: **Retry placement**.
- *The player never got the email.* The status strip lists emails that failed or may not have gone out, each with **Resend**.

Reply-To the coach who pressed Send when they coach that team, else its head coach (the trial applications address when the team has no coach on file); Cc all the team's coaches and assistant coaches, never another team's | Only when someone presses *Send "not selected" email* (the team's coach or committee edit on the Rejected card; an administrator on Offers → *Not selected*). About one team; once per player and team; never automatic | A tick (unticked, the buttons are greyed out) | The same |

The Emails page's *Overview* tab lists these (and the fee reminder, trial and account emails) in one generated table, so it can never disagree with the cards.

**Holding things back.** There is no switch to turn offers off: from 2027 they are how selection works, and there is no going back to the coach-recorded acceptance. Two controls remain. **Approval:** nothing reaches a player until an administrator approves the offer, so requests left on *To approve* wait. **Pause offer emails:** nothing is sent and queued messages wait; after a pause longer than a day, old messages are *held* for you to send or discard rather than mass-sent (a "not selected" email someone pressed during the pause is one of them: since 1.80.0 nothing else about "not selected" waits for the permission, because nothing is scheduled). Not held back by a pause: an offer approved during it is live at once (its dates run, the player can see it; only the email waits), and the coaches' "deadline not met" email goes out with the next daily check for each offer overdue then. Discarding a held offer email leaves the offer live with the player never emailed (Remind or Withdraw it). Offers already out can still be answered, paid and withdrawn while emails are paused. **Unticking an email** under Emails → *Offers and selection* is not a pause: while it is off, every one of those emails that falls due is skipped for good. Rolling back to an older version of the plugin leaves the data untouched, but an older version does not know the offer tables (and 1.76.0 to 1.78.0 would read their own switch option again).

**After a change of web address (the move to the new domain).** The permission to send offer emails belongs to the website's address, so after the change every offer, reminder and coach notice **waits in the queue** until you press *Allow this website to send offer emails* again (Emails → Offers and selection). A red warning appears on the VVL Oversight pages when the permission is closed and messages have waited more than an hour. The steps are in the move-day checklist.

The treasurer works through Held deposits and refunds by hand, so needs an Administrator account too. Players see only their own offer.

### Offers and deposits

The technical rules behind the guide above. From the 2027 season a coach's Selected or Training Only verdict becomes a place through an **offer**: the committee approves it, the site emails it, the player accepts it and secures the place with a deposit, and the club places them automatically. **Offers are how selection works from the 2027 season** (club decision, 28 Oct 2026, 1.79.0): there is no master switch, no paused state and no going back to the coach-recorded acceptance. **Seasons before 2027 never use any of it and behave exactly as 1.75.3.** The controls are the permission to send offer emails (the live-site gate, below) and the committee's approval of every offer. The one-off work switching on used to do runs by itself once per site after the update (`TeamOversight_Offers::maybe_upgrade()`, flag `team_oversight_offers_upgrade`, under a lock, audited in the log): the 2027 reset of coach-recorded acceptances, `reconcile()`, and (since 1.80.0) only a count of the rejections not told yet (below: nothing about "not selected" is sent or written by it). The 1.76.0 to 1.78.0 switch option `team_oversight_offers_enabled` is left in the database untouched and never read.

**The flow**

1. **Coach selects.** Selected or Training Only, as before. Tentative and Rejected can't be offered, and neither can payment-pending applicants.
2. **Coach presses Send offer** on the card (or **Send offers to all**). The state is *Awaiting committee approval* and **nothing is emailed**. The coach can cancel it while it waits.
3. **The committee approves** on VVL Oversight → **Offers** → *To approve*. Approval is for WordPress administrators only (there is no approve panel in the coach portal and nobody else can approve). The menu entry carries a count badge, and the list supports bulk approval, "approve all shown", and declining with a note that only the coach sees (the player is told nothing). Each row shows the player, team and role, who asked, the fee class, the quote and the deposit, any other offers or money they already have, and red reasons why a row can't be approved yet. Approval works out and stores the quote and emails the player: **To** the account's current email, **Reply-To** the team's coach, **CC** every coach and assistant of the team, including the one replies go to (who may therefore see amounts in the email), **From** the club as for every club email.
4. **The quote is fixed when the committee approves it.**
   - *Basis before the season's fees are released*: the fee matrix **upper limit** for the player's fee class and role (the Training Only cell for a Training Only offer). *After release*: the real fee for that place from the fee engine.
   - **Early Offer.** An offer quoted on the upper limit, because it was sent before the season's fees were released, is called an **Early Offer**, and it stays one after the release. The email subject and heading ("Your Early Offer to join *team* for *season*"), the offer page, the Offers to approve page and the coach's card and chip all say so (the coach sees the wording, never a dollar figure), and the email and the offer page explain it in plain words: because it's an Early Offer the season fee isn't set yet; it is set in the month fees are released (taken from the season's fee release date; January by default) and won't be more than the upper limit, $X; the deposit is 10% of that upper limit and comes off the final fee. An offer sent after release is just an offer, quoting the real fee. One helper, `TeamOversight_Offers::is_early($offer)` (with `offer_name()` and `early_note()`), decides every one of those screens.
   - *Deposit target*: 10% of the quote, in whole cents (half up). *Reply-by*: 7 days after sending. *Deposit due*: the later of the season's fixed deposit date (default 10 January) and 14 days after sending.
   - Everything is stored on the offer, so changing a setting later never moves a live offer. If the player's cell has no upper limit (or, after release, no fee) the offer can't be sent, and the coach and the administrator are told why (the coach never sees the class or any amount).
5. **The player opens the offer page** (`[team_offer]`; they must be logged in and the offer must be theirs, and anything else gets the same neutral message). It shows the team, role and season, the fee ("up to $X, set in January" or the real fee), the deposit, both dates, the commitments and the deposit policy, a **read-only preview of their Player Checklist**, and a link to the season's Trials & Team Info page. One short line follows it, chosen by the player's **age at the season start**: under 18, *Want extra training?* with the Junior Academy; 18 and over (or no date of birth on file), *Want extra games?* with the Reds Social League. The same line is in the offer email and the *you're locked in* email. They **Accept** or **Decline** (Decline has a confirm step and an optional reason that coaches see). They can't pay before accepting.
6. **Accept** gives *Accepted, deposit due* and emails the coaches. The player pays the deposit from the offer page or the Player Checklist, **in one payment**: the pay box charges exactly the remaining deposit as one fixed amount (normally the whole deposit; for a player picked by two teams it is just the difference, the top-up), with no choice of amount and no part payment, and the server refuses a payment of any other amount. Deposit money goes to this season's invoice only (it can never be used up on an older season's balance).
7. **Locked in.** When the player's payments for the season reach the target (so, when the one payment is made) the offer becomes *Locked in*: they are placed on the team automatically (a team place through the fee timeline starting that day, priced from the season start if that is later), the application is marked accepted, the coach portal moves them to **Confirmed**, and the player is emailed *you're locked in*. A target of $0 locks them in on accepting. After fees are released they pay the rest of the fee like any other fee, and may pay more than the deposit. Membership follows the placement (Full Member, as for any placed player).
8. **Decline** gives *Declined* (coaches emailed; the coach portal's Declined list).
9. **Missed deadlines.** No reply by the reply-by date, or the deposit not paid by its due date, flags the offer *Overdue* on the coach portal and emails the coaches once for that deadline. The coach decides: **Remind** (re-sends the offer email, at most once a day), **+7 days** (counted from today) or **Move to declined**. Nothing is released automatically. With one payment a missed deadline never holds money, so the player is not emailed when they are moved to Declined (there is no "offer closed" email).
10. **Fees released while a deposit is incomplete**: the target drops to 10% of the real fee. It can only go down, because the real fee is never above the limit.

**A higher team's claim comes first.** A coach can't send an offer for a team while the player is **Tentative or Selected** on another team of the same season with a *higher division* (a smaller level number above 0; teams in one division share a level, so neither is higher). **Training Only and Rejected on the higher team never block.** **JPL (U19) and U17 teams are exempt on both sides**, because juniors can play in two teams: an offer for one is never blocked, and a verdict on one never blocks another team (they are identified by the team's age rule, never by code). A Selected verdict on the higher team stops blocking once *that team's offer ended without the player joining*: declined by the player, moved to Declined, withdrawn or not approved (an offer still out, a cancelled request, a locked-in player and a player who left keep the claim). One helper, `TeamOversight_Offers::higher_team_block()`, decides, and it is enforced on the server: Send offer and Offer again are refused, the committee's approval checks again (so a claim that appears after the request refuses it, and the Offers to approve row shows the reason with Approve greyed out), and the bulk send skips the blocked players and lists them with the reason. The coach's card explains it ("Can't send yet: Tentative for State League 1 Men, a higher team. Their coach decides first."; a request already waiting reads "Blocked: ... The committee can't approve it until their coach decides.").

**Players selected by two teams.** Each offer runs its own approval, email, accept or decline, deadlines and lock-in. (Under the higher-team rule above, two offers for one player exist together when the teams share a division, when one is a JPL or U17 team, when the higher team's verdict is Training Only, or after the higher team's offer ended.) Fees use the highest bucket across a player's places, so a second place can raise the season fee; each offer's deposit target is 10% of the season fee quote with that place counted alongside their other accepted or locked-in places, and payments count across the whole season. A second offer may therefore need only a top-up, and an offer that is already locked in stays locked in.

**Changing a verdict after an offer exists.** While the offer awaits approval, changing the verdict cancels the request. Once it has been sent the coach must first **Withdraw offer** (the player is emailed a short note); if any deposit has been paid, only an administrator can withdraw, and the deposit becomes credit. A locked-in player is taken off the team the usual way (Fee timeline), which ends the offer.

**Money policy** (it is in the offer email and on the offer page):

- **If the club breaks its commitment**, the player can have the deposit back: the fee coming in above the quoted maximum, training days changing, the club withdrawing the offer or dropping them. The money stays as credit on their account and the treasurer refunds it by hand (a negative Record Payment with the order number in the note). *Offers → Held deposits* lists these.
- **If the player breaks theirs** the deposit is not refunded: declining after paying something, being moved to Declined after missing the deadline, pulling out of the team. It is kept as a negative ledger line with source `forfeit` (reversible by an administrator), written once. A locked-in player who pulls out is handled by the club personally: the money is settled as above but **no email goes out**.
- **Money above the final fee** stays as credit.
- **The upper limit is enforced.** A player whose place came from an offer quoted on the upper limit is never invoiced above that quoted amount: the cap runs inside `fee_breakdown()` (so every invoice, re-price, release and the Fee timeline preview follow it), is shown in the breakdown, and is logged once per amount. A quote on the real fee is not capped. A fee set by hand with Edit Fee is not capped either, and Edit Fee warns when it is above the quote.

**Settings.**

- *Per season* (Configuration → Offers and deposits): *Reply within* (7 days), *Pay the deposit within* (14 days) *but not before* (a fixed date, default 10 Jan of the season year) and *Deposit* (10%). The form shows the built-in value beside every field, a worked example of the dates an offer approved today would get, who saved it last and when, and a **Reset to the built-in numbers** button. The field and option names are unchanged (`deposit_date`, `percent`, `reply_days`, `deposit_days`).
- *Fee matrix*: every cell from 2027 holds two amounts, the **fee** (blank until it is set in January) and the **upper limit** (set now), for every category including Training Only and exempt $0 cells. Before release only the limit is used for quotes; after release the fee is used, capped at the limit for players quoted on it.
- *Team Management*: a **division level** per team (see not-selected, below).
- *Emails*: VVL Oversight → Emails → **Offers and selection** (the offer emails, the commitments and deposit policy, **Offer wording**, and **Pages and links**).
- *Offer wording* (1.78.0, `TeamOversight_Offer_Wording`, option `team_oversight_offer_wording`): the Early Offer explanation (five lines, with `{limit}`, `{percent}`, `{real_fee}` and `{fee_month}`, the month fees are released taken from the season's fee release date), the two money-policy sentences (`policy_club`, `policy_player`, which the commitments lists quote), the sentences the offer emails are built from (`{reply_sentence}`, `{deposit_sentence}`, `{deposit_status}`, `{reason_line}`, `{deposit_line}`, `{deposit_note}`, `{overdue_what}`), about thirty lines on the offer page, and the coach portal's flow chart, hints and confirm boxes. Each line shows its built-in text, says where it appears and what it can fill; blank or identical-to-built-in is stored as built in (so later improvements still reach it); a coach portal line may never carry a dollar figure (the save refuses it). `TeamOversight_Offers::wording($key, $vars)` is the one reader.

**The Offers page** (VVL Oversight → Offers, administrators; always in the menu since 1.79.0) has seven tabs: *To approve*, *Waiting on players* (was *Offers out*: Remind, +7 days, Move to declined and Withdraw for any offer), *Locked in* (Retry placement, Player pulled out, Withdraw), *Held deposits* (Refund owed, Club keeps it, Apply to a new offer, Reverse forfeit, and a CSV export), *Closed*, *Not selected* (1.80.0: every player and team rejection nobody has told, with the days since the verdict, *Send*, *Send all* and *Don't send*; then what was sent or stopped, and the notices from before 1.80.0) and *Setup* (1.78.0: the live setup checklist, the pages the offers link to and where everything is edited; it says plainly that the email permission and approval are the controls). Every tab opens with two sentences saying what it is and what to do there, and every tab but Setup ends with a *What the states mean* glossary. The button ids are unchanged (`mark_credit` is *Refund owed*, `forfeit` is *Club keeps it*, `pull_out` is *Player pulled out*). The same checklist is on Configuration → Offers and deposits. A status strip lists what needs a person right now (a locked-in player who isn't on the team, a fee that couldn't be priced, a deposit awaiting a decision, an email that failed or may not have been sent). Every action is a button with its own nonce and a stale-page guard. The dashboard widget has an *Offers awaiting approval* tile, Trial Applications summarises the offers by state (and Finalise becomes the retry for a placement that failed), Payment Management tags holding invoices *Deposit*, *Held* and *Forfeited* and lists recent offer alerts, and Member Lookup's Fees card lists the person's offers. Accept, bulk accept, Reject and Delete on Trial Applications refuse an application that has a live offer (finished offers are kept, never deleted, and are detached from a deleted application).

**Not selected (1.80.0, club decision, 28 Oct 2026: a coach always knows when something is being sent).** A "not selected" email is sent **only when someone presses a button**, and it is about **one team**. Nothing is scheduled, held or sent automatically: a Rejected verdict tells the player nothing, and so do the daily job and an application edit. On a Rejected player's card (2027+) the coach portal reads *Rejected - not told yet* with a **Send "not selected" email** button (anyone with edit access to that team: its coaches and committee edit; view-only and other teams' coaches are refused on the server), which asks first and says the player is told about this team only; the board has **Send "not selected" emails**, which lists exactly who on this team will be emailed (and who can't, with why) and asks before it sends. It does not wait for the player's other teams: a coach can tell a player they weren't selected for their team while other teams are still deciding or have selected them. It goes once per player and team, ever (a double press or a second tab sends nothing more), and the card then says *Not selected email sent <date> by <name>* (or that it is waiting for the permission to send offer emails); if the verdict changes later the card keeps that as history, other teams' cards show a quiet *Told they weren't selected for <team>* once the email has really gone (and say when that team has changed its verdict since), and the flow chart's side exit *Rejected, not told* counts who is left to send. What stops it (the button is greyed with the reason): an application that is no longer open, a deleted account, or the email unticked on the Emails page (a Payment-pending player can be told). **Review fixes (still 1.80.0):** it is only for a team the player applied for (coaches can mark anyone in the competition Rejected, but such a card has a quiet line and no button, and is never "not told"; since 1.80.5 the outbox checks this again just before sending, so an email pressed before that rule, or for a team the player has since taken off their application, is skipped, not sent); a player who already holds a place this season (an offer they accepted or locked in, or placed by the club) can be told one by one, but is left out of the counts, the status strip, the checklist and both send-them-all buttons, and their email suggests no other way in and promises no news about their other applications; and a pressed email that never went (discarded with the held messages, switched off, or the verdict changed before it went) counts as not told again: the card and the Not selected tab say what happened, and Send re-opens the same message, once. The email names the team; if the player applied for more than one team it says plainly that this message is only about that team and that their other applications are decided separately (it never mentions another team's decision or offer). Then it suggests **editing their application** to trial for a division below that team they are eligible for (by gender and the age rule, in division order), leaving out teams they already applied for or were turned down by, or, when there is none (or applications are closed), points adults to the Mixed Training Program and the Reds Social League, and juniors to the Junior Academy as extra training. **Who it is from** (club decision, 28 Oct 2026): it is addressed like the offer emails, all read from that team's roster when it is sent. It goes to the player's account email from the club's sender (a coach's own address can't be the From, or the mail is flagged as spoofed). The Reply-To is the coach who pressed Send when they are one of that team's coaches or assistant coaches; when someone else pressed it (committee edit in the portal, or an administrator on Offers → *Not selected*) it is the team's head coach (an assistant coach when there is no head coach), and with no coach on file the trial applications address. Every coach and assistant coach of the team is copied, including the one replies go to (never the player; coaches of the player's other teams are never copied), and it is signed like the offer emails by the Reply-To coach ("Questions? Just reply to this email and it comes straight to me", their name, "<team> coach"), or by "The <team> coaching team" when nobody on the roster can be named. The sign-off's sentences are in the offer wording registry (`ns_sign_*`); the preview and test send show a shape for a team with no coach on file (and one for a player who already has a place: eight in all), and a test still goes only to you, with no Cc and no Reply-To. The order of divisions is each team's **level** on Team Management (defaults, highest first: Premier League 1, Premier League 2, JPL, State League 1, 2, 3, U17, U15; teams in the same division share a level). **The committee's safety net:** Offers → *Not selected* lists every (player, team) rejection nobody has told, oldest first with the days since the verdict, with *Send*, *Send all* and *Don't send* (kept as a record), then what was sent and stopped, then the notices from before 1.80.0. The status strip and the setup checklist flag rejections untold for more than a week. **The 1.80.0 data step:** the old one-per-player notices are kept as history; one that had been sent (or that an administrator cancelled) was copied to each team that had the player Rejected, so those teams never offer the button again, and every other earlier rejection simply shows as not told yet. Nothing is sent by the update.

**Offer emails** (VVL Oversight → Emails → Offers and selection; wording, a preview and a test send like every club email, with a test going only to you): the offer, a reminder when there has been no reply, a reminder when the deposit is still due, the withdrawal note, *you're locked in*, three coach notices (accepted, declined, deadline not met) and *not selected*. The offer and its two reminders are previewed (and test-sent) twice, as an Early Offer and as an offer after the fees are released. They share the `{offer}` (team, role, fee, deposit and dates), `{terms}` (the commitments and deposit policy, editable), `{extras}` (one line about extra training or extra games) and `{next_steps}` blocks. **`{extras}`** is in the offer and *you're locked in* emails only: under 18 at the season start it reads "Want extra training? Have a look at the Junior Academy.", from 18 up (or with no date of birth on file) "Want extra games? Have a look at the Reds Social League." (the page's name is the link). Everyone gets exactly one; a page that isn't published leaves the line out. The two pages are the pathway pages the *not selected* email uses (Emails → Offer links), and the wording of each line is editable beside them (`{page}` is the page's name as a link; blank = built in). The Academy line is about extra training. The offer and *you're locked in* emails are previewed (and test-sent) for a player under 18 as well. Every offer email goes through an **outbox** (`team_offer_emails`) rather than being sent in the request that caused it: a message is queued once (unique key), claimed by compare-and-set and re-checked against the offer as it is *now* just before sending (an offer withdrawn while its email waited is skipped), recipients are read at send time, a failed send is retried up to three times five minutes apart, and a message that may or may not have gone (stuck in *sending*) is marked *not sure* and never retried automatically. **Nothing is sent from a site other than the one the live-site gate holds** (the box reads *Offer emails: sending is ON for / OFF on <host>*, remembers which host was given permission, and the button is *Allow this website to send offer emails*), so a copy of the database (staging) mails nobody; opening the gate first holds anything older than a day for an administrator to send or discard. A changed web address closes the gate by itself; a warning shows on the VVL Oversight pages when the gate is closed and messages have waited more than an hour.

**The one-off upgrade and rollback.** The first request after 1.79.0 (or the daily job, whichever comes first) runs `TeamOversight_Offers::maybe_upgrade()` once: it resets every 2027 coach-recorded acceptance to "offer not sent" (no offer emails had gone out), audited in `team_oversight_offer_reset_2027` (on a site that switched offers on under 1.78.0 this had already run, so it is a no-op), runs `reconcile()`, counts the rejections nobody has told (since 1.80.0 it writes no not-selected notice), then writes `team_oversight_offers_upgrade` and one log line. There is no pause other than *Pause offer emails* and approval. Redeploying an older version over this data is safe (nothing existing changes shape), but it does not know the offer tables, so don't merge accounts or release fees while rolled back.

### How it works

VVL Oversight → **How it works** (1.70.2, admins only) is a plain-English guide to the plugin for the committee and for whoever maintains it next: what it runs (with links to each admin page), how a fee is worked out, the player timeline, when money falls due, trials and payments in brief, and notes for maintainers (the public repository, how the live site pulls `main`, README and CLAUDE.md, the running version). Three parts are live, never typed in:

- **This season's settings**, for a season you pick (it opens on the current or next 2027-or-later season with dates): season dates, payment window, late-join cutoff, fee release and invoice counts, and the fee matrix.
- **Worked examples**: a full-season player, a mid-season joiner, someone who stops early, two teams at once, a backdated stop with credit, and a late joiner refused at the cutoff, each priced by the real fee engine from that season's settings and matrix, with the stretches, a small due curve (payment window shaded, a line for today) and the amounts due by each date. A season with no dates or no matrix amounts says so instead.
- **Fee calculator**: pick a season, fee class, one or two team places and an amount paid, and it shows the fee, the stretches, what is due today and by each date, the status and the pill a coach would see.

The examples and the calculator price hypothetical places in memory through the same code as every invoice and save nothing. Without JavaScript the calculator is hidden and the rest of the page still shows.

### Logs

One append-only activity log, two windows onto it (filter by event type, search by name/email/message; entries kept two years; each row stamped with when, who it was about, and which admin — or "System" for cron — did it):

- **VVL Oversight → Logs**: online and manual payments (amounts, notes, order refs), unapplied online payments (no invoice to apply them to, or a part that could not be recorded), fee payments and trial fees refunded or cancelled in WooCommerce, reminder emails sent, trial applicant emails (including any that failed to deliver), fee edits and re-prices (old → new amount, with the reason), *Manual fee kept* entries (a fee set with Edit Fee that a re-price left alone, with the amount the calculation would have set), payment arrangements recorded or ended (with the terms), 2027-and-later team place changes (*Team dates changed*: each place added, start moved, stop set, moved or cleared, role or team change and removal, with the fee before and after), and 2027-and-later season configuration (*Season dates / payment window*: each save with the old and new values, and the re-price a season-date change triggers). Bulk reconciliation backfills deliberately stay out.

### Club emails

Since 1.72.0 every email the plugin sends (the trial applicant emails and the overdue reminder) is HTML in **one club look** (`includes/class-email.php`): the logo and club name at the top, the program the email is about above its heading (*Club fees · 2026*, *Trials · 2027*), the message, and the same footer (*Questions? Just reply to this email*, the club's name and site, and why they're getting it). Each email also carries a plain-text version of the same words. Admins write the words as plain text on VVL Oversight → Emails (four tabs since 1.78.0: *Overview* with the shared Sender box and a table of every email, *Fee reminders*, *Trial applicants* and *Offers and selection*; the account emails are on Club Membership → Account Emails), with a preview of the real email beside them. Every card shows the built-in wording and a *Use the built-in wording* button, the forms save and redirect back (Post/Redirect/Get, so a refresh never sends a test again), and one rule stores wording identical to the built-in text as blank:

- a blank line starts a new paragraph, and web addresses become links;
- a paragraph starting with `>` is a highlighted note;
- `{button}` on a line of its own is the email's button (`{button:Your own words}` changes what it says);
- `{fees}` (reminder) and `{details}` (trial emails) on a line of their own are drawn by the plugin;
- the layout, logo and footer aren't editable, so emails can't drift apart. There's no need to sign off.

Under each message the page warns about anything that won't come out as meant (a placeholder the email can't fill, a block token inside a sentence, a reminder with no `{fees}`), and a customised message shows the built-in wording beside it. Wording left identical to the built-in text is stored blank ("use the default", so improvements reach it), for the reminder too since 1.72.0; a field cleared and saved goes back to the default. On the first load of 1.72.0 the saved wording was copied into new options in this format (`team_oversight_reminder_email`, `team_oversight_trial_email_texts`): changed wording kept word for word, with only the old layout swapped for blocks (the spaced-out figures for `{fees}` / `{details}`, a link on its own line for `{button}`, the hand sign-off dropped). The 1.71 options are left exactly as they were, so a site put back on 1.71 sends its old plain-text wording, never these tokens. A form from a page opened before the update is converted the same way when saved. The emails go through `wp_mail()` with the HTML type set on each message only (never site-wide), so other plugins' mail is untouched, and the logo travels inside each email (so it shows without "download images"). The Player Checklist (`[ready_to_play]`) asks logged-out visitors to log in, because the reminder's button goes there.

**Account emails (1.73.0).** Ultimate Member's emails about a member's account (welcome, activate your account, under review / approved / not approved, deactivated, deleted, reset your password, password changed, account updated) go out in the same club look, under *Your club account* (`includes/class-account-emails.php`). Ultimate Member still decides when each is sent and whether it's on (Ultimate Member → Settings → Email, which also sets their From; a Reply-To to that address is added), and supplies the member and the links; the plugin replaces the email it built, on `um_email_send_message_content`, only while Ultimate Member sends HTML email. Their subject, heading and message are edited on **Club Membership → Account Emails** (moved there from VVL Oversight → Emails in 1.78.0: same capability, same nonce, same option `team_oversight_account_email_texts`, so no data moved; blank = built-in text), with previews and a test send; Ultimate Member's own email editor no longer sets their wording (its settings page says so). Admin emails (new user, suspicious activity) are left as they are. WooCommerce's own emails are styled to match in WooCommerce → Settings → Emails (club colours, the logo header image, its Helvetica font, and the footer).

### Trial applicant emails

VVL Oversight → Emails → *Trial application emails*: one card per email with an on/off switch, subject, body and live preview. They share the page's **From** (it must be an address the server may send as), but have **their own Reply-To** — `vvldelegate@renegades.com.au` by default, editable — so applicants' questions reach whoever runs trials rather than the treasurer's inbox the fee reminders reply to. Blank means "use the reminders' Reply-To"; an invalid address is flagged on save and falls back the same way. All on by default — each is transactional (a response to something the applicant just did), never a broadcast:

| Email | Sent when |
|---|---|
| Application received | submitted with no fee due, or an unpaid application becomes confirmed |
| Payment needed | about 15 minutes after the first save with the fee due (first submission, or an edit that makes it apply; a later save while that check waits doesn't restart it, and WordPress's scheduler runs it on the next site visit), and only if it is still unpaid then |
| Payment received | paid online (sent once even though WooCommerce fires both *processing* and *completed*), or Mark as Paid |
| Changes saved | a confirmed application is edited, with no new payment (includes "didn't make this change? reply") |

At most **one email per action** — an edit that makes the fee due sends *Payment needed*, not both. *Payment needed* waits about 15 minutes from the first save with the fee due and goes only if the fee is still unpaid (1.80.3): someone who pays straight away gets *Payment received* and nothing else. A later save while that check waits doesn't restart it, and the check is a WordPress scheduled job, so it runs on the next site visit after the 15 minutes. If the check is ever lost (WordPress keeps every scheduled job in one setting, and a long request can save an older copy over it; deactivating the plugin clears them too), a backstop catches it (1.80.5): each check leaves a marker, and the daily membership job (and every later check) sends *Payment needed* for a marker more than 30 minutes overdue whose check is gone, once, still only if the fee is unpaid, with a log line saying it went late. Selection outcomes are not sent from here: **offers and selection notices are emailed only from the offer emails** (see *Offers and deposits*), and accepting, rejecting, a verdict change and Finalise themselves send nothing. Each card has a subject, a heading and the message. Placeholders: `{first_name}` `{name}` `{season}` `{trial_number}` `{teams}` (team names) `{positions}` `{fee}` `{link}`; `{details}` on a line of its own is the box with the trial number (big), teams and positions (*Payment needed*: teams and the fee), and `{button}` the button to the trial page. `{link}` is the page carrying `[team_trial_form]`, found automatically — deliberately the page rather than a one-click pay link, because a signed link would expire within a day while the page always shows the current status and, if unpaid, the Pay button. Wording left identical to the default is stored as "default", so later improvements to the built-in text still reach it; clearing a field restores the default. A mail failure never fails the submission or payment it describes — it's logged as "NOT delivered" instead. "Send test" delivers each switched-on email to you with sample data.
- **Club Membership → Logs**: the membership lifecycle — **Granted** (first membership, or one that doesn't change current status), **Extended** (same tier, new end date), **Upgraded** (e.g. Associate → Full, message shows the transition), **Expired** (logged once by the daily role sync when the last grant lapses), **Revoked** (admin action, shows the tier held), **Order refunded or cancelled** (an order that granted a membership was refunded or cancelled; the grant itself is unchanged). Past-dated grants from seeding log as "recorded".

## Club Programs

Casual programs (Mixed Development and similar) sell one WooCommerce product per program with a **variation per session date**, so "who is coming on Monday?" is already in the orders. This area reads it live — no separate attendance database.

- **Programs** are configured in Club Programs → Settings as `Name | product ID` (Mixed Development is auto-detected on first use). Each configured program gets its own admin sub-page listing its sessions.
- **Session roster**: a session picker defaulting to today (or the next upcoming session), a booked count, and one card per paying attendee — name, email, tap-to-call mobile, order number, and the same **emergency contact dropdown** the coach portal uses.
- **Guests**: someone who books multiple spots shows a `×3 (2 guests)` chip — the extra spots are real attendees whose names the club doesn't have. Orders placed without a club account show a **No account** chip (no profile, so no emergency contact — even when the order's email matches an account, since a guest checkout's email proves nothing about who placed it).
- **First-timers**: someone with no earlier session of that program gets a **👋 New here** badge and a highlighted card; everyone else shows an unobtrusive "5th session" count, and the header totals the first-timers. History is computed from paid orders for the program's product with a session date *before* the one being viewed, so booking three weeks ahead doesn't hide a genuine first-timer.
- **Ticking people off**: each card has a **Mark here** button (undo-able) that saves over AJAX — no page reload. Ticked attendees fade, strike through, and **sort to the bottom**, so the top of the list is always "still to arrive"; the header counts who's in, and each tick shows who marked it and when.
- **Multiple supervisors at once** (several courts) is safe by design: writes are atomic upserts keyed on program + session + booking, so simultaneous marks never collide or duplicate, marking someone already marked is a no-op, and every open roster polls every 20 seconds, skipping while the tab is hidden and catching up when it is shown again, so supervisors converge on the same view without refreshing. The poll sends a hash of the marks it last saw and gets back only the marks (it never runs the bookings query), or just the hash when nothing changed. The here count is worked out on the page from each booking's quantity, so a booking made after the page was opened appears, and counts, after a reload. A no-JS form fallback still works via Post/Redirect/Get.
- Ticks live in `team_program_attendance`, are explicit-state (a refresh can't flip anyone), and work identically on the front-end page and the admin sub-page.
- **Session dates**: programs can declare the weekday they run on (e.g. Mixed Dev = Tuesday). Variation labels like "13-May" carry no year, so the weekday is what pins each session to the right year — without it, last season's dates sort into this season. Pickers show the fully resolved date ("Tue 14 Jul 2026").
- **Search**: an instant filter over name and email — no page reload, sized for a phone at the door.
- **Supervisor access is per program**: each program has its own supervisors, added in Club Programs → Settings with an account search (type a name or email, click to add, × to remove), so Mixed Dev supervisors see only Mixed Dev. Administrators see everything. `[session_attendance]` shows a supervisor only the programs they run; everyone else gets a polite notice. Lock a page to one program with `[session_attendance program="mixed-dev"]`. (A pre-1.35 club-wide supervisor list is still honoured, with a tick-box in Settings to clear it once migrated.)
- **Participation stats** sit above the roster on each program's admin page, over a date range that defaults to **year to date** (with Last 12 months / All time shortcuts). Five tiles, plus a collapsible session-by-session table:
  - **Participants** — distinct people, however many sessions each booked.
  - **Newcomers** — first-ever session of this program falls in the range. Measured against *all* history, so last year's regulars never read as new, and it matches the roster's 👋 New here badge.
  - **Returning** — the remainder: they had been before the range started.
  - **New to the club** — a different question, worth seeing beside the others when a program is an on-ramp: their *account* was created in the range. A three-season VVL player trying Mixed Dev is a newcomer to the program but not new to the club. Bookings made without an account can't answer this and are reported separately.
  - **Spots booked** — guests included (a booking of 3 is one participant, three spots), with the per-session average.

  Counted from paid bookings rather than attendance ticks, so the numbers hold whether or not anyone marked people off. Sessions whose label has no readable date are excluded and disclosed rather than silently dropped.
- **Mixed Development** has its own shortcode, `[mixed_dev_attendance]`, so the club's weekly program can grow its own behaviour without touching the generic one. Both accept `history="0"` to hide the first-timer/session-count badges.

### Data imports/exports

- **RevSport CSV import** (accreditations: VA ID, payment status, coach/referee accreditation).
- **Team Lists** and **MUS Membership Report** CSV exports. Both find each person by the assignment's account (user_id) and use the email only for rows with no account id. A changed email never drops anyone, and rows with no account still list. The MUS report reads gender from both UM keys and reports anything unrecognised as Not Specified. All CSVs are UTF-8 with BOM (Excel-safe). In every admin CSV, a free-text cell (name, email, profile text) that would start with = + - @, tab or CR gets a leading single quote, so a spreadsheet never runs it as a formula. Money, phone and date columns are written as they are.

## Database tables

All created/migrated automatically on load (`TeamOversight_Database::migrate_database`); migrations are additive and idempotent.

- `team_assignments` — team/role assignments (user-ID keyed with email snapshot). From 2027 each row is one team place: `start_date` inclusive, `end_date` exclusive (the first day off; blank = still on), `is_active` worked out from the dates; written only through the fee timeline, and a stopped place is kept, never deleted
- `team_invoices` — season fee balances (user-ID keyed); `fee_overridden` (+ `fee_overridden_at`, `fee_overridden_by`) marks a fee set by hand with Edit Fee, which no re-price changes, and `fee_calculated_logged` is the calculated amount last logged for it; `payment_arrangement` (+ `_note`, `_at`, `_by`, 1.69.0) marks a payment arrangement agreed with the club, which keeps the invoice from flagging the player as not to train, and `fee_raised_at` (1.69.0) is when a re-price or Edit Fee last raised the fee
- `team_invoice_payments` — payment ledger, the source of truth for paid amounts (order-item deduped; sources: online / manual / reconciliation)
- `team_fee_segments` — dated fee-role history per member per season (2026 and earlier; not written or read for 2027+)
- `team_memberships` — membership tier grants
- `trial_applications` — applications (trial number, questionnaire JSON, fee order)
- `team_trial_selections` — per-team coach verdicts, with the player's acceptance of a Selected / Training Only offer (`offer_accepted`, `offer_accepted_at`, `offer_accepted_by`; used from the 2027 season)
- `team_trial_notes` — shared coach notes
- `team_accreditations` — RevSport data (email keyed — CSV matches by email)
- `team_activity_log` — append-only activity log (payments, emails, fee edits, grants; pruned after 2 years)
- `team_assignment_changes` — (1.70.0, written from 1.70.1) the 2027+ fee timeline's change history: one row per change to a team place (added, start or stop changed, stop cleared, role or team changed, removed by mistake, a future stop taking effect), with who, when, the old and new dates, and the fee and amount due before and after (a change that put more due on the day it was recorded is a floor for the behind clock, 1.70.2); it also holds each person's fee class history (`class_recorded`, `history_reset`). **Never pruned**, unlike the activity log, because it is the only record of removed rows. Explicitly InnoDB
- `team_program_attendance` — club program attendance ticks (one row per booking per session)
- `team_attendance` — coach-portal trial/training attendance (one row per player per team per date; unique on person + team + date)
- `fee_matrix`, `fee_matrix_versions` — season fee rates
- `fee_matrix_limits` — (1.76.0) the second amount in every fee matrix cell from 2027: the upper limit the club guarantees a fee will not exceed (no row = no limit; 0 is a real limit). The fee itself stays in `fee_matrix`, where a blank fee is simply no row
- `team_offers` — (1.76.0) one row per offer cycle from 2027: its state (awaiting approval, sent, accepted, locked in, or how it ended), the quote and deposit fixed when the committee approved it, the reply-by and deposit dates, the player's answer and the money outcome. **Never deleted**; a new offer for the same player and team is a new row
- `team_offer_emails` — (1.76.0) the outbox for offer emails: one row per message, unique on its dedupe key, so a message is queued once and sent once
- `team_not_selected` — (1.76.0; one row per application and team since 1.80.0) the "not selected" emails someone pressed Send (or Don't send) for: `team`, `state` (sent, Don't send, or refused by the outbox), who pressed it (`acted_by`, re-pointed by an account merge) and when; rows from before 1.80.0 (`team` blank, one per application) are kept as history
- `team_account_merges` — (1.71.0) one row per account merge: the kept and merged accounts, status (merged / undone), a summary, and the full backup Undo restores from (the merged accounts' users rows, profile and photos, the kept account's fields the merge changed with their values before and after, the newest club row ids at the time, and every value the merge changed)
- `team_duplicate_decisions` — (1.71.0) pairs of accounts marked as different people, with the reason, who and when; a merge carries them over to the kept account

## Season rollover checklist

1. Configuration: select the new season → set **Season Dates** (2027 on: **Season dates and payment window**, where *Paid in full by* is also the late-join cutoff), import/adjust the **Fee Matrix** (include $0 rows for exempt roles: Coach, Assistant Coach, Team Manager), review teams (age rules shift automatically).
2. Trial Applications: set the season's **trial fee product**; update the training-info page.
3. Verify the payment product and Ready to Play settings still point at the right products/pages.
4. After trials: coaches record verdicts → (2027 on) coaches press *Send offer*, the committee approves, players accept and pay the deposit → locked-in players are placed on their team automatically (**Retry failed placements**, the 2027+ Finalise, is the retry for any whose placement failed) → fees generate automatically on the release date. Before 2027 coaches record verdicts and the admin runs Finalise, as before.
5. **Offers (2027 on)**, before offers go out:
   - Configuration → Offers and deposits: the season's fixed deposit date (default 10 Jan of the season year), deposit percent (10), reply days (7) and deposit days (14).
   - Fee matrix: fill the **upper limit** in every cell that can be offered (Training Only and exempt $0 cells too). The fee can stay blank until it is set in January; *Copy fee matrix* copies the limits and leaves the fees blank for a timeline season. A fee above its limit saves with a warning.
   - Team Management: every team has a **division level** (used by the not-selected email's lower-division suggestions); the red list on Configuration names any at 0.
   - Emails → Offers and selection: create or check the **Your Team Offer** page (`/team-offer/`; it is sent with a noindex header and robots meta, so there is no by-hand SEO step), set the season's *Trials & Team Info* page and choose the pathway pages from the page lists, review the wording and send yourself a test of each email. The Offers page's *Setup* tab (and Configuration) checks all of this live. Offer emails only leave the site whose address the gate holds, so a staging copy of the database mails nobody.
   - There is nothing to switch on (1.79.0): give the permission to send offer emails on the live website only. Every offer sent before the fee release date is an **Early Offer** (quoted on the upper limit; the season fee is set in January and is never more than the limit). After the fee release date the real fee replaces the upper limit for new offers (they are ordinary offers), and unpaid Early Offer deposits drop to 10% of the real fee.
   - After the season: offers are never deleted, so a new season simply has its own rows; held deposits from the old season stay listed until the treasurer settles them.

## Development notes

- **Conventions**: all POST/AJAX handlers verify a nonce and (admin actions) `manage_options`; front-end forms use Post/Redirect/Get via `template_redirect` (never process POSTs during shortcode render — refresh would resubmit); all SQL through `$wpdb->prepare`; people are keyed by `user_id` with email kept as a display/import snapshot; roles are handled role-aware (staff assignments are never collateral damage of player operations).
- **Identity**: the fees engine resolves people via `TeamOversight_Fees::resolve_user_id()` and matches all rows with `(user_id = X OR email = Y)`, so one person's assignments/segments/invoices stay unified across account email changes.
- **One fee calculation**: `TeamOversight_Fees::fee_breakdown()` builds a person's stretches of the season (from fee segments for 2026 and earlier, from the team places' dates through `timeline_stretches()` for 2027+) and `price_stretches()` prices them (no-dates rule, clamping to the season, share, highest bucket, rounding). Both paths price through it, so there is no second copy. For 2027+ it can also price rows passed in, which is how the Fee timeline's Preview prices a change without saving it.
- **Fee timeline writes**: 2027+ team places are written only through `TeamOversight_Fee_Timeline` (`includes/class-fee-timeline.php`), which records every change in `team_assignment_changes` before writing and saves with compare-and-set, so a stale page or a second admin changes nothing and is told to reload.
- **Account merges** (`includes/class-account-merge.php`) are the one other writer of club rows' identity: they change the owner (`user_id`, and the email and name snapshots to the kept account's) of team places, invoices, payments, grants and the rest inside one transaction, and never a date, role or amount. Because a merge is blocked whenever both accounts hold records in the same season, no fee needs re-pricing. Every changed value is recorded in the merge's backup, and Undo puts back only values that still hold what the merge wrote.
- **Integrity guards**: `order_item_id` carries a UNIQUE index on both the payments ledger and membership grants (concurrent order hooks physically cannot double-apply); invoices with recorded payments cannot be deleted (zero the fee instead); overpayments (fee reduced below ledger paid, or an online payment above the balance) surface as "in credit" on the member panel and Payment Management.
- **Order storage**: all order queries are storage-agnostic as of 1.23.0 (`wc_get_orders` and WooCommerce analytics tables — no direct `wp_posts` order queries), so the plugin works under both legacy and HPOS order storage. Verify on staging before flipping HPOS on live, but it is no longer blocked by this plugin.
- **Known limitations**: read-path queries in some legacy admin *display* screens still join by email (write paths all record `user_id`); strings are not internationalised (club-internal plugin); no uninstall routine — deleting the plugin never deletes data. Overdue reminders (like all crons here) depend on WP-cron, which fires on site traffic. Multi-step money operations are not wrapped in DB transactions (the ledger + recompute design makes partial failures recoverable rather than corrupting).
- **Local dev**: Docker copy of the site; lint against PHP 7.4 (`php -l`); deploy by copying the plugin folder into the container. Production pulls this repo's `main` branch from GitHub: a push doesn't deploy by itself, but the Deployer for Git plugin on the live site pulls within about a minute of one (after the planned hosting move, the host's own Git deployment will pull it instead), so treat every push to `main` as going live.
