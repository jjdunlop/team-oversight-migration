# Team Oversight — AI maintainer guide

Read this before changing anything. The README covers *what the plugin does*;
this file covers what you need to know to work on it safely.

## What this is

Custom WordPress plugin running MURVC (Melbourne University Renegades
Volleyball Club) on **members.renegades.com.au**. It manages memberships,
VVL competition trials, coach selections, team assignments, fees/payments,
and pre-season readiness. It integrates:

- **Ultimate Member (UM)** — accounts, profiles, login
- **WooCommerce + Square** — all payments (memberships, trial fees, club fees, kit)

Pushing to `main` deploys to the LIVE site via Deployer for Git. Treat every
push as a production deploy: lint and test first (see Workflow below).

## File map

- `team-oversight.php` — bootstrap: requires classes, `create_tables`, cron teardown. Version lives here TWICE (header + `TEAM_OVERSIGHT_VERSION`) — bump both.
- `includes/class-database.php` — table creation + `migrate_database` (additive, idempotent, runs on every load; structural steps guarded so a normal load issues no ALTER), team config (`get_teams_config`), age rules / DOB cutoffs. `assignment_changes_table_sql()` is the one definition of the fee timeline's change table, shared by `migrate_database()`, `create_tables()` and `team_oversight_create_tables()`.
- `includes/class-admin.php` — all VVL Oversight admin pages (trials, assignments, payment management, configuration, readiness) + menu registration.
- `includes/class-members-page.php` — Club Membership admin: Members list, Membership History, MUS Matrix, VV Report, seeding, order re-scan.
- `includes/class-member-lookup.php` — Club Membership → Member Lookup: search-first single-person view (profile, emergency contacts, grants, assignments, fees, trials, orders, activity) over *all* accounts, not just ledger members. Never lists accounts — searches are capped and require a term. Search covers emergency-contact name/number too (reverse lookup); phone matching is digits-to-digits so formatting and missing leading zeros never block a match.
- `includes/class-stats-page.php` — Club Membership → Stats: data-quality snapshots/trends and postcode distribution + watchlist, scoped to current ledger members.
- `includes/class-memberships.php` — membership tier engine: grants ledger, product/category → tier mapping, order hooks (processing/completed grant; refunded/cancelled only flag — `flag_reversed_grants()` logs `membership_order_refunded` once per grant and never ends or deletes it), role sync, cron, paged order re-scan.
- `includes/class-fees.php` — fee matrix, season dates, pro-rata, fee segments (dated fee-role history), invoice generation, and the fee timeline groundwork (1.70.0: `timeline_applies()`, the payment window readers, Configuration's readiness box).
- `includes/class-payments.php` — payment schedule/overdue, `[member_fees]`, pay-any-amount checkout flow, payment ledger.
- `includes/class-trials.php` — `[team_trial_form]`, trial fee payment flow, trial numbers, eligibility. `parse_assigned_team()` / `describe_assigned_team()` are the one reading of the trial_applications.assigned_team format (one bare code, or comma-joined bare codes with ' (T/O)' after Training Only teams, as Finalise writes it); player-facing text must go through `describe_assigned_team()`. class-admin undo/remove still parse it inline, and the Finalise button count matches its tokens in SQL — keep all of them in step if the format ever changes.
- `includes/class-trial-emails.php` — transactional emails to trial applicants (received / payment needed / payment received / changes saved), settings on VVL Oversight → Emails. **Never add an email for selection outcomes** (accept, reject, finalise, a player's acceptance of an offer) — that is a deliberate club decision, not an omission. Send points must fire once per state change: gate on the UPDATE's affected-row count, since WooCommerce fires both processing and completed.
- `includes/class-committee-access.php` — committee access to the coach portal (option `team_oversight_committee_access`, user id => `view`|`edit`; admins are always `edit`) + the VVL Oversight → Committee Access page.
- `includes/class-coach-portal.php` — `[team_coach_portal]`: selection board, verdicts, notes, roster export. Also owns the shared card helpers other areas reuse: `get_emergency_contacts()`, `render_emergency_details($email, $user_id, $email_fallback)`, `format_phone()`, `phone_tel_href()` (all public static).
- `includes/class-programs.php` — Club Programs: casual-program session attendance read live from paid orders (product per program, variation per session date), admin sub-page per program (with year-to-date participation stats: participants / newcomers / returning / new-to-club, newcomer measured against all history) + `[session_attendance]` for supervisors.
- `includes/class-readiness.php` — `[ready_to_play]` checklist + Player Readiness admin. `compute($user, $season)` and `get_player_teams()` count active assignments only, which is what the player sees. Only the admin page passes `$include_verdicts = true` to add coach verdicts.
- `includes/class-imports.php` / `class-exports.php` — RevSport CSV import; team list / MUS CSV exports. `TeamOversight_Exports::csv_cell()` (public static) is the shared formula-safe CSV text cell every export uses, the coach roster included.

## Domain glossary

- **Season** = calendar year string ('2026'). Season dates (start/end) are configured per season and drive all pro-rata and overdue maths.
- **Membership tier** = time-bound grant in `team_memberships` (life/full/associate). Highest unexpired grant wins. End date >= 2099-01-01 means "never expires" (life). Grants come from purchases (product meta or category rules), manual admin grants, seeding, or team assignments — an assignment for season Y grants Full Member until **1 April of Y+1** (`assignment_grant_end()`), so VVL players stay members until the next season's teams are finalised. `TeamOversight_Memberships::covered_until($user_id, $tiers, $date)` is the read-only API other plugins use (the Reds Social League checks full/life cover with it) — keep its signature stable.
- **Assignment** = a person on a team for a season with a role: `playing_member`, `training_only`, `coach`, `assistant_coach`, `team_manager`. One person can hold several (incl. coach + player on the same team).
- **Verdict** = a coach's per-team call on a trial applicant: tentative / selected / training_only / rejected. Verdicts are NOT assignments; the admin "Finalise Coach Selections" converts selected/training_only verdicts into assignments + invoices. From the 2027 season (`TeamOversight_Coach_Portal::offer_acceptance_applies()`) the flow is **offer → accepted → finalised**. A selected/training_only verdict is an offer. An editor of that team (`get_editable_team_codes`) records the player's yes in the portal (`team_trial_selections.offer_accepted` / `_at` / `_by`, coach_action `set_offer`), and Finalise places only accepted offers. Any verdict change clears the acceptance, Selected ↔ Training Only included; so do the portal's clear and `sync_trial_after_assignment_removal()`. Payment pending applicants can't hold an offer. Seasons before 2027 ignore acceptance completely. Recording or undoing an acceptance is a selection outcome, so the never-email rule applies to it too. Player-facing pages ([ready_to_play]) learn a selection only from active assignments, never from a verdict or an acceptance.
- **Fee segment** = dated stretch of a member's season in `team_fee_segments`; since 1.65.0 its `buckets` column holds every active team bucket (team, role, fee class) as JSON (older rows have only `fee_role`, priced at the person's single class). Stretch rate = the highest bucket (since 1.66.0 — no coaching discount); coach / assistant coach are priced at the supporter amount and team manager at the playing member amount (`TeamOversight_Fees::CHARGED_AS`), so the matrix only needs playing_member / training_only / supporter. Season fee = Σ stretch rate × share of season. **`TeamOversight_Fees::fee_breakdown()` is the only place this is calculated** — invoices and the Payment Management breakdown both use it; don't add a second calculation. It builds the stretches and hands them to `price_stretches($stretches, $season)` (1.70.0), which does the pricing: the no-dates rule, clamping to the season, each stretch's share, the highest bucket and the single rounding. It is public so the fee timeline prices its own stretches through the same code; change pricing there, never in a copy. Assignment changes checkpoint segments; payments are never re-charged. A segment opened after the person's history closed starts no earlier than the last one ended (`next_segment_start()`, shared by the checkpoint and fee_breakdown's not-yet-recorded stretch so a reactivation never overlaps), and an invoice whose owner left every team before the season started re-prices to $0 whatever the matrix says (`left_before_season()`; it also checks under the invoice owner's account, because a re-price can run under an old email that no longer resolves to them and must never zero someone still on a team; invoices with no segment history, and matrix gaps mid-season, keep their amount).
- **Fee class** (2027+, `TeamOversight_Fees::SEASON_CLASS_RULES_FROM`) is judged at a fixed point for the season. Junior = `birth_date` (`/`→`-`, validated Y-m-d) on or after `TeamOversight_Database::get_dob_cutoff('u19', $season)`. Alumni = `degree1enddate` before `TeamOversight_Fees::fee_class_reference_time()`, which is MIN(`created_date`) of the person's fee segments for the season (the first checkpoint; now if none). `checkpoint_fee_role()` writes `created_date` in site time for this reason. The class itself is not frozen: `current_buckets()` reads the live profile on every checkpoint, so a profile edit moves the person from the next re-price; only the reference moment and the cutoff are fixed. 2026 and earlier, and calls that pass no season, keep the age/degree-end-on-the-day rule in `determine_fee_class()`. Don't change that path, because live 2026 invoices and open segments depend on it. Display code that explains a class (Payment Management's fee-info line, the team view's MUS Category) must pass the season and judge the same way, or it contradicts the invoice.
- **Fee standing** (1.69.0, club decision) = how far someone is behind the linear payment schedule, in time: days from the earliest date an invoice of theirs at least $1 overdue fell behind (`get_overdue_since()`: the paid-through date, or a past season's end) to today, across ALL their invoices, so an earlier season's leftover counts. Behind means at least $1 overdue in total; if only small amounts add up to it, the latest of their dates is used (and their seasons named), so cents on an old invoice never age a fresh debt. An invoice is never behind from before it was billed: the date is raised to the later of `created_date` (the database clock: read as `UNIX_TIMESTAMP()` and formatted with `wp_date()`, so each date gets its own daylight-saving offset) and `fee_raised_at`, because pro-rated joins, late releases and mid-season rises are priced from that day, not the season start. `TeamOversight_Fees::fee_rise_fields()` stamps `fee_raised_at` on every rise (a lower fee or a re-save never restarts the clock). Every rise does, even back up to an amount held before: a "highest amount" rule was tried and flagged players the day they rejoined after a drop, so where the clock can't be exact it errs towards not flagging. `apply_invoice_amount()` and Edit Fee both use it, so **any new writer of `invoice_amount` must merge `fee_rise_fields()` too**. The schedule still runs from the season start (`get_overdue()` is unchanged), so a new joiner must catch up with it from the day they're billed; the planned fee timeline (each player's own payment window) replaces this stopgap. 30 days or more (`TeamOversight_Payments::STANDING_FLAG_DAYS`) flags them as not to train. `TeamOversight_Payments::get_fee_standings($people, $season)` is the only place this is worked out (one invoice query for a whole list); the coach portal's confirmed players and Payment Management both call it, and `describe_standing()` / `describe_behind()` word it. Invoices belong to their account: an invoice with a `user_id` matches only that account, and only one with no account (or a person with none) goes by email. Matching by email alone once showed one member's debt on whoever later used that address. An invoice with `payment_arrangement = 1` still counts as behind but never towards the flag, unless its fee was raised after the arrangement (`fee_raised_at > payment_arrangement_at`, both site time): a rise counts again until the arrangement is recorded again. `set_payment_arrangement()` (Payment Management → Arrangement / Extend arrangement, logged once as `payment_arrangement`) marks the chosen invoice and every other invoice of that person with money owing, and ending clears all of theirs, so an arrangement covers the person's debt, not one season; it uses the same identity rule as the standing. Payment Management shows the person's arrangement (`arrangement_held`, the most recently recorded, overdue or not) on every season's row, with Extend arrangement where that row's fee is owing but not covered and End arrangement wherever they have one. Arrangements don't touch the overdue reminder emails, and `describe_duration()` (the email's `{time_overdue}`) keeps its weeks-until-60-days wording.
- **Fee timeline** (planned for the 2027 season on; `TeamOversight_Fees::FEE_TIMELINE_FROM`, `timeline_applies($season)`: a `/^\d{4}$/D` season from 2027). Each team place's own start and stop dates will set the fee, and each player's fee will fall due across their own part of a payment window. **1.70.0 ships only the groundwork: nothing prices, schedules or validates with it yet, so every season still charges and falls due exactly as in 1.69.** What exists: the `team_assignment_changes` table (InnoDB, created behind a SHOW TABLES guard). It will hold every change to a team place's dates, team or role, with who, when, and the fee and amount due before and after. **Never prune it and never delete from it**, unlike `team_activity_log`: it will be the only record of removed rows and of the behind clock's floor. Nothing writes to it yet. `get_payment_window($season)` returns `from` (Fees due from) and `to` (Paid in full by), each falling back to the season start or end, plus `from_set` / `to_set` and `raised_at`; it returns null when the season has no dates. `latest_start_date($season)` is the effective Paid in full by (the late-join cutoff). The window has its own non-autoloaded option (`PAYMENT_WINDOW_OPTION`, `team_oversight_payment_window`), which nothing saves yet. It is kept out of `team_oversight_season_dates`, so that option's shape (`start`, `end`) and `get_season_dates()` never change; the season-date save merges into the season's entry rather than replacing it, so a key added there later survives a date change. The log types `team_dates` and `season_config` are registered ahead of 1.70.1, their first writer, so don't remove them as unused. Configuration shows a read-only *Fee timeline readiness (for the 1.70 upgrade)* box for 2027+ seasons: counts of the season's places, blank dates, segments and invoices, the release state, and the database version and table engines.
- **MUS** = Melbourne University Sport (the club reports member matrices to them). **VV** = Volleyball Victoria. **VVL** = Victorian Volleyball League.
- **Trial number** = per-season sequential number given at application, players write it on themselves at trials.
- **Payment pending** = a trial application in `awaiting_payment` (fee unpaid). Since 1.63.0 it never expires: coaches see it, flagged and sorted to the bottom of every section, and can note or reject it, but Tentative / Selected / Training Only are refused until it's paid (`handle_actions`, plus disabled dropdown options). `expired` is a legacy status, revived once by migration.

## Hard-won gotchas (do not rediscover these)

- **Target PHP 7.4.** No PHP 8 syntax: no `str_contains`, no null-safe `?->`, etc. Lint with `php -l` under 7.4 before every push.
- **UM meta formats:** gender lives under TWO keys. `gender_dropdown` (plain string) is what the Member Profile and rego forms write **today**; `gender` (serialized array `a:1:{i:0;s:4:"Male";}`) is the **older** key left on earlier accounts. Always read through `TeamOversight_Database::get_member_gender()` (current key first, older as fallback); SQL reports use `COALESCE(NULLIF(gd.meta_value,''), g.meta_value)` then `maybe_unserialize`. Reading `gender` alone once blocked every member who'd filled their gender in on the profile form from submitting trials. `birth_date` is `YYYY/MM/DD` (convert `/`→`-` before `strtotime`).
- **People are keyed by `user_id`;** email is a snapshot for display/CSV matching. Some old admin read paths still join by email — new code must write user_id and prefer it on reads.
- **Order queries are storage-agnostic (1.23.0+)**: `wc_get_orders()` and WooCommerce analytics tables (`wc_order_stats`, `wc_order_product_lookup`) only — never query `wp_posts` for orders in new code, so the plugin keeps working if/when HPOS is enabled. When using `wc_get_orders`, always pass `'type' => 'shop_order'` (it returns refund records otherwise). Membership grants fire on order status → processing/completed only, and only for orders linked to a WP account (guests grant nothing).
- **Money invariants**: `order_item_id` has UNIQUE indexes on the payments ledger and membership grants — never remove them; insert failures there are the dedupe working, and `record_payment()` returns false (no recompute, no log) when its insert fails. An online fee payment that spans several invoices, or pays more than is owed, writes several ledger rows, but only the FIRST carries `order_item_id` — that insert is the claim, and an order hook that loses it writes nothing. Later parts carry `order_id` with `order_item_id` NULL and a note (`Part n of m of order item #X`, or `Overpayment, ...` for money above the balance, which goes on the newest invoice as credit). Never pass the same `order_item_id` to more than one `record_payment()` call. Money that can't be recorded is never dropped silently: a payer with no invoice (or no account any more), and a first part that fails while no other hook holds the claim, both flag the item `_murvc_fee_payment_unapplied` (final — no later hook applies it) and log the whole amount as `payment_unapplied`; a later part that fails is logged as `payment_unapplied` for its amount (the claim already stops re-fires). Never write `outstanding_amount` directly — money moves only via `TeamOversight_Payments::record_payment()` / `recompute_invoice()`. Fees-engine identity goes through `TeamOversight_Fees::resolve_user_id()` with `(user_id OR email)` matching — keep that pattern in any new query so email changes never split a person. WooCommerce refunds and cancellations never move money or change status automatically. `TeamOversight_Payments::handle_payment_refund()` / `handle_payment_cancelled()` and `TeamOversight_Trials::handle_trial_refund()` / `handle_trial_cancelled()` only log `payment_refunded` / `trial_fee_refunded`. They log once per refund (order item meta `_murvc_refund_alerted_<refund id>`, or `_murvc_refund_alerted_cancelled`), and only for orders that reached the books: a ledger claim or an unapplied flag, or an application whose order_id is that order. `TeamOversight_Log::render_alert_notice()` lists the last 30 days on Payment Management and Trial Applications; entries never clear when handled, so the treasurer puts the order number in the Record Payment note and checks Logs / Member Lookup before entering one. Automatic negative ledger rows (deduped by refund id) are deliberately not built yet.
- **Teams are per season (1.48.0+).** The registry options `team_oversight_teams` / `team_oversight_team_meta` are keyed `CODE-YYYY` (`SL2M-2027`); assignment/application/selection rows keep the BARE code plus their `season` column — never write a suffixed code into a data row. Always call `get_teams($season)` / `get_teams_config($season)` with the season in hand (they return bare-code keys); the no-argument form falls back to the admin's remembered season and is only for legacy callers. Un-suffixed registry keys are the pre-1.48 global list, kept as the fallback for seasons never seeded. `seed_season_teams()` copies a list forward and is a no-op when the season already has entries.
- **Trial submissions are serialised per season** with a MySQL named lock (`TeamOversight_Trials::submission_lock_name()`, `GET_LOCK`). The "existing application?" check, the next number (`max(MAX(trial_number), mark) + 1`, where the mark is the non-autoloaded option `team_oversight_trial_number_mark_<season>`, read straight from the database), the insert/update and the raise of the mark must all stay inside it. Moving any of them out reintroduces duplicate applications and duplicate or reused trial numbers (a double-tap once created two applications for one player). Trial numbers are never reused: anything that deletes an application calls `TeamOversight_Trials::retire_trial_number($season, $number)` before the delete (it takes the same lock and only ever raises the mark), as Trial Applications' delete does. If the database can't do named locks, the save proceeds unlocked rather than failing.
- **Fee release dates (1.64.0+)**: before a season's release date `generate_invoice()` creates nothing, re-prices nothing (not even an existing invoice — a withdrawn $0 invoice holds credit), and returns false (it still checkpoints fee segments); `withdraw_unreleased_invoices()` deletes unpaid early invoices and drops paid ones to $0 so the ledger total shows as credit; `apply_fees_for_season()` invoices everyone on release (daily via the membership cron, or "Release fees now"). Callers must not treat that false as a failure — check `TeamOversight_Fees::fees_released($season)` first (bulk accept used to roll back the whole batch on it). Clearing a release date that hasn't been applied yet releases the season (`apply_fees_for_season()`, like Release fees now); clearing one that was already applied only removes it, so nothing is re-priced. Saving a passed date on, or clearing the date from, a season already being charged calls `apply_fees_for_season($season, true)`: new invoices only, never a re-price of existing ones, so Edit Fee survives a mistaken future date being put back. 'Already being charged' means its release was applied, it had no date before, or `invoices_still_out()` (some invoice > $0 and none at $0 holding payments, i.e. not taken back by Remove fees until release). A real first release (nothing out yet, or fees taken back), Release fees now and the daily release still re-price everyone except manual fees (see Manual fees stick, below). `invoices_still_out()` counts automatic invoices only, on both sides (charged, and $0 holding credit), because a manual fee survives Remove fees until release; so do the Configuration page's *issued before the release date was set* warning, its Remove fees until release button and confirm, which list manual fees on a line of their own. `apply_invoice_amount()` logs every re-price it is given a reason for (old → new). `apply_fees_for_season()` also returns `partial` (priced, but a role had no matrix amount, from `fee_breakdown()['missing']`), `unpriced` (an existing invoice kept because nothing could be priced; not counted in `updated`) and `manual` (fees set with Edit Fee, kept; not counted in `updated`). Every release notice and log line reports all three.
- **Finalise Coach Selections only invoices what changed.** `run_finalise_selections()` holds a per-season named lock (`murvc_finalise_<prefix><season>`), matches existing playing rows and invoices by the application's account as well as its email, never changes an existing row's role (it lists verdicts that differ), and calls `generate_invoice()` only for players it added to a team this run or who have no invoice yet. Don't widen that to everyone: on an existing invoice `generate_invoice()` re-prices to `fee_breakdown()`, so a blanket re-run re-prices every automatic invoice. Manual fees are safe since 1.68.5 (`fee_overridden`); its notice counts them as kept via `last_kept_manual()`. Its button count is Selected / Training Only verdicts not reflected in assignments — every one on a pending application, but on an accepted one only when the verdict's `TEAM` / `TEAM (T/O)` token isn't in `assigned_team` (new or changed since the last Finalise), so a placed player whose row has since gone never prompts a re-run that puts them back — plus finalised players still on the verdict's team with no invoice once released. From 2027 the `$selected` query and both button counts also require `offer_accepted = 1`; keep all three in step. Unaccepted offers are never finalised. The Trial Applications page lists them on every load, button or not, via `report_unaccepted_offers()` (Finalise itself doesn't, because the page renders straight after it). `get_unaccepted_offers()` splits them into waiting and already on the team, where any active playing row on that team counts, whatever its role; the second group covers an acceptance withdrawn or a verdict changed after Finalise. The portal's undo says so too when the player is already on the team. Never point admins at Undo Assignment for one team: it removes every team on the application. In those seasons `assigned_team` keeps teams placed by an earlier run whose acceptance was later withdrawn, because Finalise never undoes anything.
- **Manual fees stick (1.68.5, club decision).** Edit Fee (`ajax_update_invoice`) sets `team_invoices.fee_overridden = 1` with `fee_overridden_at` (site time) and `fee_overridden_by`. From then on no automatic re-price changes the fee. The check is `TeamOversight_Fees::fee_is_manual()` in `update_existing_invoice()`, so every `generate_invoice()` caller is covered: Finalise, Accept, bulk accept, the trials accept path, `recalculate_after_assignment_change()` (add / change / delete / Undo), `apply_fees_for_season()` (Release fees now, the daily release, a passed or cleared release date). `withdraw_unreleased_invoices()` skips manual invoices too, and Undo Assignment never deletes one. **Any new re-pricing or invoice-deleting path must respect the marker.** Route it through `generate_invoice()`, or check `fee_is_manual()` before writing `invoice_amount` or deleting. As a backstop, `apply_invoice_amount()` (the only automatic writer of `invoice_amount`) updates only where `fee_overridden = 0` and then recomputes and logs nothing, which also closes the race with an Edit Fee saved mid re-price. Fees set by hand before 1.68.5 are not marked (no safe backfill, and data rows are never rewritten); they stick only once re-saved with Edit Fee. The fee segments still checkpoint as usual and the ledger is never touched. When a re-price is skipped, `note_manual_fee_kept()` logs `fee_manual_kept` with the amount it would have set, but only if that differs from the manual fee and isn't `fee_calculated_logged` already. Edit Fee and Use calculated fee reset that column, and so does a re-price whose calculation equals the manual fee (so a later swing back to an amount is logged again). **Use calculated fee** (`ajax_use_calculated_fee` → `use_calculated_fee()`) clears the marker and re-prices through `generate_invoice()` under the owner's current account email. A person with a manual fee who leaves every team keeps it: nothing re-prices it, and Payment Management flags them (warning list + *On no team now*) instead. Callers that count re-prices check `last_kept_manual()` after `generate_invoice()`.
- **Exact dates of birth on coach cards and in the trial book are deliberate.** Coaches need them for Volleyball Victoria age cutoffs and exemptions at trials (over-age flags show *born dd/mm/yyyy*, and the trial book prints the date). This is not a privacy bug, so don't remove, mask or round it. Access is already limited to who may view the team (`can_view_team()`, coach access ending with the season).
- **Role-aware operations:** never let player-row operations delete coach/manager assignments (this bug happened twice). Any DELETE/UPDATE on assignments must filter by role. Removing a player follows one path — delete the role-filtered rows by id (matched by user_id OR email), `sync_trial_after_assignment_removal()` (Selected verdicts drop to Tentative, or the next Finalise silently re-adds the player; a Team Assignments inline edit that makes an active playing row inactive, moves it to another team or turns it into a staff role is a removal too, and `ajax_update_assignment` syncs on that change), then `recalculate_after_assignment_change()` — and deletes an invoice only after that re-price, when it has no ledger rows and nothing accrued (Undo Assignment used to do both wrong). That deletion rule is `TeamOversight_Fees::delete_invoice_if_empty($email, $season, $invoice_id)` (1.70.0, moved out of Undo unchanged): no active team place left that season, no ledger rows, not a manual fee, accrued under $0.005. Use it rather than writing another. `sync_trial_after_assignment_removal()` is public static since 1.70.0, so code outside the admin class can call it. Re-price under the account's current email (row user_id, else `resolve_user_id()` worked out *before* the delete), never the deleted row's email snapshot: once its last row is gone an old email resolves to no one, the person's other teams drop out of `(user_id OR email)`, and someone still on a team is under-priced (`ajax_delete_assignment` once did exactly that; Undo and Finalise use the account email too).
- **Coach portal styling is self-contained (1.61.0+).** The theme restyles `.button` (cyan, square, uppercase) and native fields look different per browser, so the portal defines its own control set at the end of its `<style>` block, scoped under `.coach-portal` with `--cp-*` tokens: `.button` = navy primary (the main action in a spot), add `coach-btn-secondary` for everything else (white, navy outline); expanders are `details.coach-app-details > summary`. New controls must use these classes rather than inline styles or new one-off button looks. Keep expander rules on `> summary` — the note Edit link is a `<summary>` nested inside the Notes expander.
- **Always `wp_unslash()` free text from `$_POST`/`$_GET` before sanitising** — `sanitize_textarea_field(wp_unslash($_POST['x']))`. WordPress adds magic-quote slashes to all request input (AJAX too), so skipping it stores `I\'ve` and `\"quoted\"`; coach notes and trial answers shipped like that until 1.62.2 (a one-off repair, `repair_magic_quotes()`, cleaned the saved data). Codes, seasons and enum values don't need it; anything a person types does.
- **Member-controlled text is untrusted in admin pages too.** Display names come straight from the UM profile forms (accounts auto-approve), so admin JS builds suggestion lists with `document.createElement` + `textContent` + `addEventListener` — never a template string into `innerHTML` or an inline `onclick` (a name could run script as the admin, and an apostrophe stopped people being picked). Display names are stored entity-encoded (`&` as `&amp;`), so decode them with a detached `<textarea>` (set its `innerHTML`, read `.value`) and assign the result with `textContent`: that one `innerHTML` is safe only because a textarea parses its content as text and never creates tags. Use a textarea for this and nothing else — on any other element the same code runs markup — and don't remove the decode, or names with `&` show and fill as `&amp;`. A season read from `?season=` or the remembered user meta must match `/^\d{4}$/D` before it is used, remembered or echoed (anything else falls back to the remembered season, then the current year), and `admin_url()` output goes through `esc_url()`.
- **Front-end forms use Post/Redirect/Get** via `template_redirect` + flash transients. Never process POST during shortcode render (refresh resubmits).
- **Every admin POST/AJAX handler**: nonce + `current_user_can('manage_options')`. Coach portal: server-side check that the user may act on that team — `get_editable_team_codes($season)` for anything that changes data (verdicts, attendance, notes), `can_view_team()` for reads (portal, team CSV, trial book). Never gate on `get_my_teams()` alone: committee members (1.62.0+) reach teams they don't coach, and view-only ones must be refused edits server-side, not just shown no buttons.
- **Coach portal privacy.** A coach assignment opens its season only until `assignment_grant_end($season)` (1 April the year after): `get_coach_assignments()` drops ended seasons via `coach_access_open()`, and every gate builds on it, so never query coach rows for a gate around it (committee access is separate). Emergency contacts are looked up by `user_id` — pass it to `render_emergency_details()`; the email is only a fallback for legacy rows with no user_id, and Club Programs turns the fallback off because a guest order's email proves nothing. Application answers shown to coaches go through `coach_visible_form_data()`, which shows a club waiver as just Waived by club; the stored `Trial Fee` keeps the full reason and its `CLUB_WAIVER_PREFIX` (the player-edit path relies on the prefix, admins see the reason). A confirmed player's card is the team list (1.69.0): `render_card_expanders(..., $trial_tools = false)` leaves out Notes and Attendance, there's no Mark attended, and `render_fee_standing()` shows their fee standing as **percentages only — never a dollar amount**, because fees differ by class and some are set by hand (a reduced fee would show). Everyone who can view the team sees it; amounts stay on admin pages. A stale portal nonce returns `expired_notice()` (reload wording, never retry); expired-page notices carry the coach-portal-expired class, which keeps the portal pop-up on screen until tapped, and the verdict JS treats a non-JSON reply (WordPress answers 0 once the login lapses) the same way.
- **Migrations are additive and idempotent** (`migrate_database` runs on every request: front end, AJAX, cron). Never rename/drop columns; add and backfill. Every structural step must sit behind a cheap check (SHOW COLUMNS / SHOW TABLES / SHOW INDEX / a one-off option flag) so a normal load runs zero ALTER TABLE. An unconditional ALTER, even a MODIFY that changes nothing, takes an exclusive metadata lock and rewrites the table definition, so every page load queues behind any open transaction on that table (two unguarded MODIFYs on fee_matrix and trial_applications ran on every request until 1.67.7).
- **The live site also runs WPCode snippets outside this repo** (annual profile-update wall, admin tools). If behaviour on live isn't explained by this codebase, check WPCode. Long-term, prefer moving snippet logic into the plugin.
- **The DB table prefix is not the WordPress default** — always use `$wpdb->prefix`, never hardcode a prefix.
- **Dates you stamp use the site's clock.** WordPress runs PHP in UTC, so `date('Y-m-d')` is still yesterday until late morning in Melbourne. Stamp dates with `current_time('Y-m-d')` (or `wp_date()`), as Finalise, Accept and bulk accept do for assignment start dates, Team Assignments does for end dates (Inactive, the past-end-date check) and the fees engine does for segments. Mixing the two clocks shows an end date before the start date. SQL `CURDATE()` follows the database clock (UTC on the local mirror, and almost certainly on live), not the site's, so it lags the site by up to 11 hours. Membership grants are dated in site time too (`current_time('Y-m-d')`, or the order's local paid date), so every active-today check (memberships, the Members page, Member Lookup, revoke) binds `current_time('Y-m-d')` and never uses `CURDATE()`/`NOW()`.
- **Neutralise member-controlled text in CSV cells.** A cell starting with `=` `+` `-` `@`, a tab or a CR gets a leading apostrophe so a spreadsheet never runs it as a formula. There is one helper for this, the public `TeamOversight_Exports::csv_cell()`; the admin exports and the coach roster CSV all call it, so don't add a second copy of the rule. Apply it to free-text columns (names, emails, positions, profile text) only — never to phone, date or money columns (credits are negative), where a leading `+` or `-` is real.
- **Never load a year of orders in one request.** Page `wc_get_orders` (`'type' => 'shop_order'`, `'limit'`, `'page'`, ID order) and clear the runtime cache between pages. `rescan_paid_orders()` shows the pattern, including the time budget and the resume cursor.
- **A log type must be registered in class-log.php's channel list in the same commit that first writes it.** Each Logs page shows only its own channel's registered types, so an unregistered type is stored but never shown.
- **Commit messages must not contain double quotes** (PowerShell + git arg-passing mangles them on the maintainer's machine).

## Development workflow

There is a **local Docker mirror** of the site (containers `murvc_wp`,
`murvc_cli`, `murvc_db`; site at `localhost:8080`; WP root
`/var/www/html`), seeded from a database dump. The loop that works:

1. Edit code in this repo.
2. Lint: `docker run --rm -v <repo>:/code php:7.4-cli php -l /code/includes/<file>.php`
3. Deploy to local: `docker cp <repo>/. murvc_wp:/var/www/html/wp-content/plugins/team-oversight-migration/`
4. Test end-to-end with a PHP script run via `docker cp script.php murvc_cli:/tmp/ && docker exec murvc_cli wp eval-file /tmp/script.php --path=/var/www/html`. Pattern: create throwaway users/orders/grants, exercise the real code path (not a reimplementation), echo OK/FAIL lines, clean up. Use far-past seasons (e.g. '1990', '2098') to avoid colliding with real data. Use reflection for private methods.
5. Bump the version (both places), update README if behaviour changed, commit, push — **push = live deploy**.

## This repo is PUBLIC — privacy rules

The repo must never contain member or club-sensitive data. Concretely:

- Never commit database dumps, CSV exports, screenshots of admin pages, or
  test fixtures containing real names, emails, phone numbers, or DOBs.
  Test scripts must generate throwaway users (`@example.test` emails) and
  delete them.
- No credentials, API keys, security-plugin details, or infrastructure
  specifics (server paths, DB names/prefixes, hosting) in code or docs.
- Server logs (`error_log`) never get member emails or names — log
  `user #ID`; a gap admins should act on also goes to `TeamOversight_Log`.
- The local Docker mirror contains real member data — it stays on the
  maintainer's machine, never in this repo, and its dumps are confidential.
- When documenting a data issue, describe the shape, not the people
  ("older accounts use a legacy field", not counts of identifiable groups
  or examples with real values).

## Invariants to preserve

- Deleting the plugin must never delete data (no uninstall routine — intentional).
- Payments/ledger rows are never mutated by fee recalculation; outstanding = fee − paid, always.
- A fee set with Edit Fee (`fee_overridden = 1`) is never changed by automatic re-pricing — only by Edit Fee again or Use calculated fee.
- Dedupe rules: membership grants by `order_item_id`; payment applications by order item (only the first part of a split carries it; an item flagged unapplied is never auto-applied); re-running any seeding/re-scan/finalise tool must be a no-op the second time.
- Season rollover requires zero code changes (age cutoffs, fees, teams all derive from config + season year).
